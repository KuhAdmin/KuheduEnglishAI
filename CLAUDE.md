# CLAUDE.md — Kuhedu Lingo AI

Guidance for Claude Code (and humans) working in this repository. Read this fully before making changes.

## 1. Product

**Kuhedu Lingo AI** is a mobile-first Progressive Web App for learning **spoken English** through conversation with an AI tutor (similar in spirit to SuperNova AI). Core experiences:

- **AI conversation practice**: the learner speaks and the AI tutor replies with voice and text, in role-plays and free talk.
- **Pronunciation & fluency feedback**: per-word scoring, grammar corrections, better phrasings.
- **Structured lessons**: levels (CEFR A1–C2), daily goals, vocabulary, listening drills.
- **Progress & motivation**: streaks, XP, history of sessions, review of mistakes.

The primary device is a **mid-range Android phone on a 4G connection**, used one-handed. Design and engineer for that first, then scale up to tablet and desktop.

We build **one piece at a time**. Do not scaffold features that were not asked for. When a task touches an area not yet built, leave a clear `TODO(feature-name)` rather than inventing it.

## 3. Project structure

Feature-based structure. Code lives with the feature that owns it; only truly shared code is promoted to `shared/`.

```
src/

  app/                 # App shell — the only place that wires features together
    App.tsx            # Starts what the loaders count on (lesson content, the learner's data,
                       #   who is signed in), then makes the router: in that order
    router.tsx         # createAppRouter(): each feature's exported routes under the layouts
    layouts/           # RootLayout (theme + PWA, draws nothing)
                       # PhoneFrame (the phone learner screens are drawn in: the device's own
                       #   screen on a phone, a phone in the middle of the display when wider)
                       # PhoneLayout (puts every learner route in PhoneFrame)
                       # ScreenLayout (safe areas + gutter for screens outside the main tabs)
                       # TabsLayout (the main screens, with the bottom navigation)
    routes/            # App-level route elements (RouteError / not found) and loaders
                       #   (whereTheyLeftOff: who sees the landing page, and where the rest go)
    providers/         # AppProviders, queryClient
    pwa/               # usePwaUpdate (service-worker registration + update state)
    styles/index.css   # Tailwind entry; imports shared/styles
  features/

                       # voices), voices (picking one), useVoices, useVoiceStore (two voices per
                       # language, one per tutor), lipSync and useLipSync (a face's lips, following the sound),
```

Folders are created when first needed; don't add empty ones.

Rules (the import rules are enforced by ESLint):

- A feature **must not** import from another feature's internals; only from its `index.ts`. If two features need the same thing, move it to `shared/`.
- `shared/` must never import from `features/` or `app/`.
- **Routing:** each feature exports its routes from `index.ts` using `lazy: async () => ({ Component: (await import('./pages/XPage')).XPage })`, so every screen is its own chunk. Keep `index.ts` light — never re-export page components statically from it.
- Use `paths` from `@/shared/lib/paths` for every link and route path; never hard-code URL strings.
- All learner-facing text goes through `useT()` (see "Screen texts and languages" below). No literal UI strings in learner screens.
- Call the backend only through `apiRequest(path, { schema })` from `@/shared/lib/api/client`, which validates every response with Zod and turns a refusal into an `ApiError` carrying the server's `code` and `fields`. (No screen calls it yet: see "Backend" below.)
- **Layouts:** learner routes sit under `PhoneLayout`, which draws them in the phone frame (see §5, "The phone frame"). Full-bleed screens (landing, onboarding steps, the placement test and its result, a week's overview, a day of lessons, a setting opened from Profile) are its direct children and handle their own safe areas; the four main screens (Home, Learn, Progress, Profile) go under `TabsLayout`, which adds the bottom navigation; any other learner screen (sign in / sign up, practice) goes under `ScreenLayout`, without it. The admin area is outside `PhoneLayout`, in its own wider `AdminLayout`, and is never framed. **Everything under `PhoneLayout` except the landing page and the account screens sits under one guard, `requireAccount`** (see "No guests" below): a new learner screen goes inside that group in `app/router.tsx`, never beside it.
- **Route map:** `/` landing · `/sign-in` and `/sign-up` (one screen, two halves) · `/onboarding` (redirects to its first step) · `/onboarding/language` · `/onboarding/profile` · `/onboarding/placement` · `/placement-test` (the test) · `/placement-test/result` · `/home` (the 50-week journey) · `/home/sections/:section` (a section's weeks) · `/home/weeks/:week` (a week's overview) · `/lessons` (the Learn tab) · `/lessons/weeks/:week/days/:day` (a day of lessons, 1 to 7; on Day 6, `?part=quiz` and the like open one part of the review; on Day 7, `?scenario=2&level=easier` opens a challenge) · `/progress` · `/profile` (the menu of settings) · `/profile/language` · `/profile/appearance` · `/profile/voice` · `/profile/tutor` · `/practice` (not in the navigation) · `/admin` (redirects to texts) · `/admin/texts` · `/admin/curriculum` · `/admin/lessons` · `/admin/landing` · `/admin/languages` · `/admin/profiles`.
- **Entry flow:** landing → sign in / sign up → the emailed code → onboarding. The landing page's "Get Started" opens `/sign-up`, its "Sign in" link opens `/sign-in`. **There is no way into the app without an account.**
- **No guests.** The app is for someone signed in to an account whose address is verified (decided 2026-10-12, once creating an account worked; before that a visitor could "Continue as Guest"). Without one, only the landing page and the account screens open (`/`, `/sign-in`, `/sign-up`, `/verify-email`, `/forgot-password`). Every other learner route is behind the loader `requireAccount` (`features/auth`), which leads someone who is not signed in to `/sign-in` and a sign-up whose code was never entered to `/verify-email`; an admin has an account too and may walk the learner's screens. It runs on the way in and is not run again at each step taken inside (`shouldRevalidate`). Both it and the front door go by `accountStanding()` (`shared/lib/account`): the server's word, waited for at most `SESSION_WAIT_MS` (2 s) from when it was asked.
- **Offline, the app still opens for a learner who was signed in.** Who is signed in is never kept in the browser, but one word is (`kuhedu-signed-in`, written by `session.ts` at every answer of the server's, cleared when it says nobody or on sign-out): an account was signed in here when the server last said. It is read **only while the server cannot be asked**, never for the admin area, and it opens nothing the server keeps. Without it a dropped connection would lock every learner out of lessons that are already on their phone.
- **The landing page is for someone without an account.** `/` is also the address the installed app opens at, so its loader (`openWhereTheyLeftOff`, in `app/routes/whereTheyLeftOff.ts`: the one place that knows, since it spans onboarding, placement and lessons) asks where they stand: **nobody signed in → the page, whatever this browser holds**; a sign-up whose code was never entered → the code step; an account → on from **where they left off in this browser**, by the furthest thing they did: any lesson heard or done, or a placement test with an outcome → Home; a placement test begun and not finished (the same one its own screen offers back) → the test; onboarding's question about themselves answered → the placement intro; nothing of theirs at all (a new account) → onboarding. **How far they got is kept with their account**, so the loader first waits for the account's data to reach this browser's stores (`learnerDataSettled`, 4 s at most: see "A learner's data" under Backend), and their account on a new phone opens where they were. With the server unreachable it goes by what the browser holds. **Having only chosen a language is not a beginning**: it is chosen on the landing page itself. **An admin with nothing of a learner's here is let through**, because the page is theirs to edit — but an admin who has also used the app as a learner in the same browser is sent on like one.
- **A learner's way in after signing in is that same front door**: sign-in and the account screen's "Continue" lead to `paths.landing`, not to Home, so one rule decides. A feature that needs to say how far a learner got exports a reader for it that works outside a screen (`hasAnsweredAboutThemselves`, `placementProgress`, `hasLessonProgress`); add to `leftOffAt` when a new stage of the way in is built.
- **Onboarding steps** (in order: language → profile → placement intro) are built with `StepScreen` (`shared/ui`, also the frame of the placement test's screens): heading, scrollable content, primary action pinned in the thumb zone. Questions use `ChoiceList`. The learner's language is saved in `useLanguageStore` (shared, see below); other answers (`ageGroup`) in `useOnboardingStore`. Each new step gets its own path under `/onboarding/`, and the previous step's Continue navigates to it.
- **Age groups** (`child` 6–12, `teen` 13–18, `adult` 18+) are fixed in `shared/lib/learner/ageGroups.ts`, not admin settings, because content and safety rules will branch on them.
- Use the `@/` path alias for `src/` (e.g. `@/shared/ui/Button`).
- One component per file. File name = component name in PascalCase (`ChatBubble.tsx`). Hooks are `useXxx.ts`. Non-component modules are camelCase.
- Colocate tests (`Button.test.tsx`) and stories/examples next to the component.

### Backend (`server/`, `packages/contracts/`)

**Built on the server so far: its foundations, the tables, accounts, a learner's own data, the app's voice, checking a recorded word, and checking a spoken reply.** It starts, answers `GET /api/health` (which also says whether the database is reachable) and turns every failure into one shape. **Accounts are real** (`/api/auth/*`, see "Accounts" below): the account screens talk to the server. **What a learner sets and does is kept with their account** (`/api/me/*`, see "A learner's data" below). **The lessons are kept in the database** (`/api/lessons`, see "Lesson content" below); the rest of what an admin manages (the landing page, the languages, the screen texts, the course's wording) is still kept in the admin's browser. The order of what comes next: that rest of the admin content, events, privacy (export and delete), then AI.

**The app's voice is the exception, and already comes from the server:** everything said aloud is fetched from `/api/speech/*` (see "Voices" below). Those routes need no database and ask for no account: a sound says nothing about anyone, and it is kept by its address.

- **The tables** (`server/src/db/schema/`, 17 of them): accounts (`users`, `oauth_identities`, `sessions`, `email_codes`, `audit_log`), the learner (`learner_profiles`, `learner_photos`, `lesson_marks`), the placement test (`placement_sessions`, `placement_responses`, `placement_results`), `events`, and what an admin manages (`app_config`, `text_overrides`, `week_content`, `content_history`, `assets`). The AI tables (speech attempts, conversations) are not there: they come with the AI work.
- **Admin content is kept in three shapes**, and in all three only what an admin wrote is stored — the built-in content stays in the app: `app_config` holds `landing`, `languages` and `learner-profiles` whole; `text_overrides` holds one row per reworded text (scope `screen` or `curriculum`, a language, a key); `week_content` holds one row per kind and week (the ten `week-…` settings objects, split by week). `content_history` keeps what a row held before a save replaced it.
- **Lesson progress is rows that are only ever added** (`lesson_marks`: a week, a kind — `heard`, `day`, `review_part`, `scenario` — and which one), so sending a mark twice changes nothing, and what a phone did before its account kept anything on the server (or while offline) is added without conflict.
- **Table conventions:** UUID keys, every time a `timestamptz` (`instant`), and a list of allowed words is `text` with a `CHECK` (`oneOf`), never a PostgreSQL enum. What Zod checks, the database checks again: weeks 1 to 50, days 1 to 7, language tags, the lists. Those lists are written beside the tables and repeat the app's for now; each moves to `@kuhedu/contracts` when its resource is wired, as the learner's and the placement test's have. **A `CHECK` must not hold a `;`**: the tool that writes migrations cut one off there (a `data:` URL's `;base64,`), silently.
- **Deleting an account removes everything of the learner's** (`ON DELETE CASCADE`); what an admin wrote stays, without their name (`SET NULL`). `email_codes` is kept by address, so the route that deletes an account removes those itself. `server/test/schema.test.ts` holds this, and that no table change is missing from the migrations.

- **One shape for every failure:** `{ error: { code, message, fields? } }` (`apiErrorSchema` in `@kuhedu/contracts`). `code` is one of a fixed list (`validation_failed`, `unauthenticated`, `forbidden`, `not_found`, `conflict`, `rate_limited`, `unavailable`, `internal`); `fields` maps a form field to a screen-text key; `message` is for logs and developers and is never shown to a learner. A route refuses by throwing `HttpError`; anything else that throws is logged and answered as `internal` with nothing of the cause.
- **Schemas are written once, in `@kuhedu/contracts`**, and imported by both sides. The schema half of an app file (a settings object, the placement session) moves there when its resource is wired, file by file; the hooks stay in `src/`. Contracts and server files import with the `.ts` extension, because Node runs them as they are.
- **Same origin.** The app calls `/api/...`; in development Vite proxies `/api` and `/media` to the server on `127.0.0.1:8787`, **passing on the address the browser asked at** (`changeOrigin: false`, which a proxy target written as a bare string turns on): the server refuses a request that changes something unless its `Origin` names the host it was asked at (`plugins/security.ts`), so with the host rewritten every sign-up and sign-in from a browser was a 403. Whatever stands in front of the server in production must do the same. Keep the path prefixes the service worker has rules for: `/api/app-config`, `/api/lessons`, `/api/conversation`, and `/api/speech` (a sound is kept for good once heard; the list of voices is refreshed behind).
- **Secrets are the server's.** They are read in `server/src/env.ts` from the environment, or in development from `server/.env`, which git ignores. Never a `VITE_*` variable, never the repo, never a log: `readEnv` names a wrong setting without repeating its value. The database is given as `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`.
- **The database changes only through migrations** (`server/src/db/migrations`, applied in order by `npm run db:migrate -w @kuhedu/server`). Write a table in `src/db/schema/`, then `npm run db:generate -w @kuhedu/server`; never change a database by hand, and never edit a migration that has been applied.
- **`buildApp()` starts nothing**, so tests drive it with `inject` and need no database; a test that needs one says so.

### A learner's data (`server/src/modules/me/`, `src/shared/lib/learnerData/`)

**Everything a learner sets or does is kept with their account, and a browser that is signed out holds none of it** (asked for by the user on 2026-10-13: "Let it be saved per user"; asked what, they chose all of it; asked what signing out does, they chose that it clears). Before, it was one browser's and nobody's: an account on a second phone began from nothing, and two people on one phone saw each other's settings, photo and progress.

- **What:** the Profile settings (language, appearance, the tutor's two voices per language, the tutor's face), the answer about themselves (age group), their own photo, lesson progress, and the placement test with its result. **Not** the tutor's mute (the device's), the placement test's event log (`TODO(analytics)`), or admin content.
- **Screens read the stores exactly as before, and never wait for the server.** No setting has a loading state. One module, `learnerSync` (started by `App.tsx`; a unit test that does not start it has stores that are the browser's alone), fills the stores from the account when someone signs in, sends each change, and empties them when the server says nobody is signed in. Offline, the app runs on what the browser holds and sends what changed when it can.
- **The rule, by who the server says is signed in and whose the browser's data is** (`kuhedu-learner-sync` remembers that it is an account's, which changes are unsent, and which photo is here; **never whose**): a learner and an account's data → the account's replaces it, save for changes not sent yet (**pull**); a learner and nobody's data → it fills what the account lacks and becomes the account's (**adopt**); nobody and an account's data → every store back to its default (**clear**); nobody and nobody's → nothing, so a visitor's language chosen on the landing page stays. Another account taking the browser over with no sign-out between is cleared first.
- **Per kind of data** (each a `LearnerPart`, registered with `registerLearnerPart` from beside its store, so `shared/` never imports a feature): profile fields are **last change wins, field by field** (`profileFields.ts`; a feature adds one with `registerProfileField`, as onboarding does); lesson marks are **only ever added, so the two sides are joined** (`progressPart.ts`); of two placement tests **the one touched later stands**, and a result is the latest finished (`features/placement/store/placementSync.ts`); the photo is fetched only when the account's stamp is not the one this browser holds (`photoPart.ts`).
- **Where the account already has an answer, it wins over what a visitor chose before signing in**: someone who picked Bengali on the landing page and signs in to an account set to Hindi gets Hindi. Settings follow the account.
- **Signing out sends what is unsent first** (`onSigningOut`), then the clear follows from the server's answer: so every way of signing out, and a session that ran out, are one rule. After it the landing and account screens are in English until a language is picked.
- **The routes** (all behind `requireVerified`, checked before the body is read; 120 a minute for each learner): `GET /api/me` (`{ profile, progress, placement }`, progress in the store's own shape), `PATCH /api/me/profile`, `GET` / `PUT` / `DELETE /api/me/photo`, `POST /api/me/progress/marks` (up to 200; one sent twice changes nothing), `PUT /api/me/placement/sessions/:clientId` (a finished test is not reopened: 409). **Whose it is comes from the session only**: nothing in a request names a learner. Contracts: `api/me.ts`, `api/placement.ts` (the placement schemas and lists moved there; `features/placement` re-exports them).
- **The photo is the small picture the app already makes** (a `data:` URL, at most `LEARNER_PHOTO_MAX`), kept in `learner_photos` so that no other read carries it, checked by its first bytes to be the kind it says, and **given back to its owner only**. A profile says when it was saved, never the picture.
- **The theme is kept as its id and checked for form only**: which themes exist is the app's to say, and one this build does not have is passed over. "Follow the device" is kept as no choice at all. A voice chosen when the app used the device's own voices names nothing the server has, and is not sent.
- **Known and accepted:** data already in a browser from before this is adopted by whoever signs in there first (nothing stored says whose it was); a session that runs out while changes made offline are unsent loses them; a result whose own test was since replaced by a new one in that browser cannot be sent (`TODO(placement)`).
- **Not built:** exporting or deleting what is kept (`TODO(privacy)`), and the journey's current week, which is still the stop-gap.
- **Tests:** `server/test/me.db.test.ts` (against the test database, run alone), `learnerSync.test.ts` and each feature's own (`placementSync.test.ts`, `useOnboardingStore.test.ts`) with the calls mocked, and `e2e/learnerData.spec.ts` against an in-memory stand-in (`learnerServer`). **Every other spec starts with `/api/me` unreachable** (`withoutLearnerServer`, in the `test` fixture), so it runs on what it seeded.

### Lesson content (`server/src/modules/content/`, `packages/contracts/src/content/`, `src/shared/lib/curriculum/weekContentRemote.ts`)

**A week's lesson content is kept in the database, and that is where every device reads it from** (asked for by the user on 2026-10-13: "Wire up the lessons content with database for Week 1"). Before, a week was either built into the app's code or an admin's edit that only that admin's browser held.

- **One row per week and kind** (`week_content`; `WEEK_CONTENT_KINDS`: `picture`, `dialogue`, `vocabulary`, `sentences`, `roleplay`, `challenge`, `quiz`, `review_dialogue`, `review_roleplay`, `scenarios`), so a phone downloads the week it opens, not all 50. Each row's `value` is that week's entry of the settings object the screens read.
- **What a piece is, and how one is read back, is written once, in `@kuhedu/contracts`** (`content/lessons.ts`: the types, the limits and a `parse…` for each kind; `parseWeekContent(kind, value)`). The app's `week….ts` files re-export from there and keep only what is the app's (the built-in Week 1, the hooks, the helpers that need a learner's language). **The server stores what `parseWeekContent` makes of a save**, so a row is always something a screen can show; a save with nothing usable in it is refused.
- **Reading:** `GET /api/lessons/weeks/:week` answers anyone with every kind (`null` where nothing is kept), with an `ETag` and `no-cache`, so an unchanged week costs a learner almost nothing. **The screens read exactly as before**: the `week-…` settings objects are now this browser's copy of the server, and `ensureWeekContent(week)` fills it. It is awaited by the loaders of a week's overview and of a lesson day, **for 1.5 s at most**; with the server slow or unreachable the screen opens on the copy from last time, or on what is built in, and follows if the answer comes later. No screen has a loading state for content. **A router runs the first screen's loaders the moment it is made, so `App.tsx` makes it (`createAppRouter()`) only after `startLessonContent()`**: made as its file was read, a lesson opened by its own address asked for its week before anything was fetching, and showed "coming soon".
- **Week 1 is in the database** (put there from `server/content/week-01.json`, which is the built-in content written out). **The copy in the app's code stays as the fallback** for a phone that is offline before it has ever fetched the week, and for the tests. An admin's edit of Week 1 is a row like any other; "Use built-in" removes the row.
- **Weeks 2 to 50 are written as files and imported** (`npm run content:import -w @kuhedu/server -- content/week-02.json`): `{ "week": 2, "content": { "dialogue": { … }, … } }`, each piece as an editor would save it. Every piece is read with `parseWeekContent` before anything is written; one with nothing usable stops the file, and one that lost something on the way in (a text over its limit, a turn without its reply) is named. A kind left out is left as it is; one given as `null` is removed. **The user gives a week's English; the assistant writes the Bengali and Hindi and imports it** (decided 2026-10-13; the translations are `TODO(content)`: native review, like the rest).
- **Writing a week from the syllabus** (Weeks 2 to 15 were, on 2026-10-13: the user gave, for each week, a competency and five "micro-learning units", one per core day, each a title and an outcome; the assistant wrote all the English as well as the Bengali and Hindi, `TODO(content)`: review). The days keep their fixed forms, so **each day's content carries that day's unit**: Day 1's conversation opens on unit 1 but walks through all of the week's units, so that nothing is asked of a learner later that they have not heard; Day 2's words are unit 2's, Day 3's sentences unit 3's, Day 4's role-play turns on unit 4, and Day 5's challenge is unit 5, under the unit's own title. Day 6 (quiz, a second conversation and a short role-play with other people) and Day 7 (three scenarios in other places) are written to match. **A unit's title is shown nowhere but on Day 5**: the days' headings are the app's ("Watch and listen"), and a day has no field for a name of its own.
- **Rules the content is written by:** a learner's own answer is a frame, not somebody's answer ("I live in …", "My favourite food is …"); **a sentence a learner translates from Hindi never depends on their gender** ("मुझे … पसंद है", "मेरा … है", "मैंने … की": never "करता हूँ"; a question to "आप" takes the usual plural), and a cue speaks of the partner without a gendered verb ("उनके रहने की जगह पूछें"), because either tutor plays them; in a conversation, where the speakers are known, the Hindi is theirs. **A role-play partner says nothing of themselves that only a woman or only a man could**, has the other name where the name is one (`asWoman`, `asMan`), or is a role ("the clerk", "the manager", "the teacher"). Every piece is written exactly in the shape it is read back in, so the import reports nothing tidied.
- **The section's milestone** ("introduce themselves for about one minute, ask basic questions and respond without reading a script") **is Week 5's Day 5 as far as it is built**: the one-minute introduction, recorded and ticked off by the learner. Nothing assesses it (`TODO(assessment)`).
- **Writing:** Admin › Lessons (and the weeks' pictures in Admin › Curriculum) save to `PUT /api/admin/lessons/weeks/:week/:kind` (`requireAdmin`, checked before anything is read), only the weeks that changed, each with the version it was written from. **Another admin's save in between is not written over** (409: the Save bar says so and keeps what was typed). `DELETE` removes a piece. Each save keeps what the row held before (`content_history`) and says who made it (`audit_log`). `useSettingsDraft` sends a save there for any settings object that is the lessons' (`lessonsRemote(name)`), and to this browser for every other.
- **Before an editor opens it has everything the server keeps** (`ensureAllLessonContent`, in the admin routes' loaders), with each piece's version. **Lessons an admin wrote in a browser before the server kept any are given to the server once**, the first time that admin opens an editor there; until then a week the server has nothing for is left alone in that browser (`kuhedu-lessons-on-server`).
- **"Reset to defaults" on the Lessons page now removes what was written for every week, for everyone**, and its question says so. What it removed is in `content_history`, and whatever was imported is still a file in `server/content/`.
- **Pictures are still kept inside the content** (a word's, a partner's, the week's own, as `data:` URLs the admin area makes), up to 1.5 MB a piece: a week with many is a heavy download (`TODO(assets)`: upload them and keep an address).
- **The database gives an object's keys back in an order of its own**, so content is never compared letter for letter on the server (`asText`), and in the app it always goes through its parser, which puts it back in the order the screens and the editors expect.
- **Tests:** `server/test/lessons.db.test.ts`, `weekContentRemote.test.ts` (the calls mocked), `e2e/lessonContent.spec.ts`, which also opens all seven days of each week written in `server/content` (**add a new week's number to its list**; a role-play partner given an `asMan` name is shown under it, since the default tutor is a man). In a unit test nothing starts it (`startLessonContent` is the app shell's), so the settings are the browser's alone as before. **Every browser spec starts with the lesson routes unanswered** (`withoutLessonServer`), and an admin gets a stand-in that keeps what they save (`lessonServer`, given by `signInAsAdmin`).

### Voices (`speech/tts/`, `server/src/modules/speech/`)

**Everything the app says aloud is said on our own server: by Kokoro-82M in English and Hindi, by AI4Bharat's Indic-TTS in Bengali. The device's own text-to-speech is not used anywhere** (decided for quality: the same voice on every phone; and for cost: no fee per use).

- **Shape:** the app asks `GET /api/speech/audio?voice=&text=` and plays the MP3 it gets; `GET /api/speech/voices` lists the voices. The Node server checks the request (a voice that is offered, a text of 1 to 400 characters), limits each address, keeps every sound it has made on disk (`server/var/speech`, named by a hash of model, voice and text) and asks the Python service (`speech/tts`: FastAPI on `127.0.0.1:8788`, `npm run dev:speech`) only for a sound it does not have. No account is asked for, and it needs no database. When the service is down the list of voices is empty, sounds already made are still served, and a new one is refused as `unavailable`.
- **A sound's address is its name**: the same voice and text are the same sound for good (`Cache-Control: immutable`). So "Play slowly" is the same sound at a lower `playbackRate` with its pitch kept, never a second sound.
- **With a sound comes the mouth for it** (the `X-Speech-Mouth` header; `speech/tts/mouth.py`, `speechMouthSchema` in `@kuhedu/contracts`): `0c450m625r925c`, thousandths of a second and a letter for the shape the lips take from then on (`c` closed, `m` nearly closed, `o` open, `w` wide, `r` round). It is not an estimate: Kokoro decides how long every sound of a sentence lasts before it makes the speech, and those lengths add up to the speech exactly (checked against the model, and in a browser against the sound). Which sound gets which shape is a table in `mouth.py` (`TODO(content)`: an animator's eye); its one rule is that **the jaw opens on every vowel and comes up for the consonants between**, so no vowel shares the consonants' shape — when two did, "together" was one still mouth for most of a second. **Bengali's mouth is close, not exact** (`mouth_of_letters`): Indic-TTS too decides each letter's length first and those lengths add up to the speech, but measured against the sound a vowel that opens a word ("আপনার") is heard 60 to 100 ms from the time the model gave it; and it is made from letters, not sounds, so the jaw opens for a consonant's unwritten vowel wherever the spelling says it is there, which is not everywhere a speaker says it. Nobody has looked at the tutor's lips in Bengali yet (`TODO(content)`).
- **A sound is kept only with its mouth**, by the server's shelf, the browser and the service worker alike: one that came without (a speaking service older than the server, mid-update) is answered `no-store` and made again next time, so no face is left guessing for good. For the same reason the address the app asks at also names what comes with the sound (`&with=lips`, which the server does not read): a browser's copy from before the mouth was sent is not that sound. **Change what travels with a sound and that word must change too.**
- **Languages:** American and British English, Hindi, and Bengali. There is no Indian-English accent.
- **Bengali is said by AI4Bharat's Indic-TTS** (`speech/tts/indic.py`; decided 2026-10-13, by ear). Kokoro was never taught Bengali. The first build had Kokoro's Hindi voices read it (`bn_alpha` and three more, from sounds eSpeak NG wrote): the user listened to that beside Indic-TTS, called it awful, and it is gone. Indic-TTS is a model taught Bengali itself (FastPitch and HiFi-GAN, run by the library Coqui TTS), with a woman's voice and a man's. The model calls them only `female` and `male`, so **their names are ours: `bn_diya` (Diya) and `bn_arjun` (Arjun)**. A learner's saved `bn_alpha` names nothing the server has and is passed over, like any stale choice. **No Bengali speaker other than the user has listened yet** (`TODO(content)`).
- **Its model is fetched by hand, once on each machine** (`python -m tts.indic_fetch bn`: 1.5 GB into `speech/.models/indic-tts`). Without it the service still starts, says so, and lists no Bengali voice: Bengali is then silent, with nothing to change in the app. `TODO(ops)`: the licence of the model files and of the IIT Madras recordings behind them was not found (the repository is MIT); read it before this speaks to real learners.
- **It reads Bengali letters only, so a Bengali text is prepared first** (`speech/tts/bengali.py`): a number becomes its word, and **an English word inside a Bengali sentence is respelled in Bengali letters and said by the same Bengali voice** (decided 2026-10-13, over switching to the English voice mid-sentence), from a list of the words the course quotes (`RESPELLED`) or else from its sounds. `TODO(content)`: a Bengali speaker's review of that list. The model also gave back up to a second of quiet around every sentence; that is cut to a breath and a pause.
- **Coqui TTS is older than the PyTorch and `transformers` it runs on here**, and is held up in three small places, all in `indic.py` and explained in `speech/README.md`. **After upgrading `torch` or `transformers` in `speech/.venv`, say a Bengali sentence before anything else** (`python -m tts.samples bn_diya`). On this laptop Smart App Control also needed `scikit-learn==1.8.0`: a blocked `scikit-learn` breaks `transformers`, and with it Kokoro.
- **Each voice names the model that says it, and the server keeps a sound under that name** (`MODELS` in `voices.py`, `modelOf` in `speaker.ts`; the app is not told). So changing how Bengali is prepared means changing `indic-tts-v1` there: every Bengali sound is then made afresh and Kokoro's are untouched. A browser that heard the old one keeps its copy.
- **Another Indic-TTS language** (it has thirteen) needs its model fetched, a reader for its script beside `bengali.py`, and its two voices in `INDIC` in `voices.py`. Hindi stays Kokoro's.
- **Silent, with the text still shown** — never another voice, never another language: a text in a language without a voice; a sound not heard before while the server cannot be reached. What was heard once plays offline (service worker, `CacheFirst`). Screens say "cannot be played right now", not "this device cannot".
- **The voices on offer** are in `speech/tts/voices.py`: those Kokoro's model card grades C or better, best first, without the whispered one (`TODO(content)`: a teacher's ear on the list). One of Kokoro's own voices says its language and gender in its id (`af_heart`), a Bengali one does not (`bn_diya`); the app reads both from the list and never from the id, so nothing is guessed. Each language has a default voice for each gender; English's are American, the better made. **Adding a language or a voice is done there and nowhere in the app.**
- **A first hearing waits.** On a plain processor a sentence takes about as long to make as it lasts (measured on a 2-core laptop: 1.0 to 1.4 times for Kokoro, 0.6 to 1.0 for Bengali), and the service loads both its models before it starts answering (a minute or two; about 1.5 GB of memory with both). **Kokoro asks the model hub each time it starts**, and on a poor connection that start can hang for many minutes (seen 2026-10-13); with every file already fetched, `HF_HUB_OFFLINE=1` starts it without asking. The parts of a conversation are asked for in the order they are heard, never all at once, or the first line would wait behind the last. `TODO(content)`: make the built-in content's sounds ahead of time.
- **On a developer's machine** the app is silent unless `npm run dev:server` and `npm run dev:speech` are both running. `speech/README.md` has the set-up: Python 3.10 to 3.12 (Kokoro does not run on later ones yet), and nothing to install on the system.
- **Tests:** `pytest` in `speech/` (fake synthesisers, no model; how a Bengali text is prepared, and both mouths, on fixed numbers), `server/test/speech.test.ts` (a fake speaker), and in the app `src/test/fakeSound.ts` (`installFakeSound()`: a fake server and player that record what was said, in which voice and at what speed).

### Speech scoring (`speech/`)

**Speech is scored with open-source libraries on our own machine, never by a paid speech API** (decided for cost: no fee per use).

**A learner sees what the scorer found on Day 2, marked every time as a first version that can be wrong** (decided by the user on 2026-10-13, asked who should see it). This replaced the earlier rule that no learner sees a verdict until the scorer is right 8 times in 10 on recordings of our own learners. **That measurement has still not been made**: the only clips it has heard are a machine's voice. So: the note that it is new and can be wrong is part of the result and is never dropped (`lessonDay.feedback.firstVersion`); only Day 2's words and Day 3's sentences have it; and nothing may be built that counts on it being right (no score, no progress, no lock, no "you passed"). The role-plays have a check of their own, on the words of a reply and not on how it sounded (see "Checking a reply" below). Every other screen where the learner speaks still judges nothing, and says so.

- **The path:** on Days 2 and 3 a recorded take gets a button, "Check how I said it" (`PronunciationCheckAction`), with what it does said beside it. On the tap the app turns its own recording into a WAV (`shared/lib/audio/wav.ts`: one channel, 16 kHz, so the server needs no `ffmpeg`) and sends it to `POST /api/pronunciation/assessments?word=&parts=&stress=` (`server/src/modules/pronunciation`, behind `requireVerified`, 20 a minute for each learner). The Node server passes it to the scoring service (`speech/assess/service.py`, `npm run dev:scorer`, on `127.0.0.1:8789`, `SCORER_URL`) and answers with findings; `PronunciationFeedback` says them from stored texts (`lessonDay.feedback.*`).
- **A recording is a person's voice, and is kept nowhere.** It is sent only on that tap, never by itself; held in memory by the Node server and by the scorer for as long as judging takes; never written to disk, never kept with the account, never logged, and nothing is recorded of what was found. So there is nothing of it to delete.
- **What a learner is told is decided on the server** (`findingsToShow`): a finding under `PRONUNCIATION_SHOWN_FROM` (0.5, **an untuned guess**, in `@kuhedu/contracts`) is dropped, so that the scorer's faintest suspicions are not told as corrections (it is 7% sure the stress of a right "hello" moved); several sounds that differ are one line; and which sound was heard as which is not sent, because the scorer writes those in phonetic letters. With nothing sure enough, the answer is `ok`.
- **A sentence (Day 3) is judged by its words, not its parts.** The scorer says which word a differing sound was in, and the server passes on those words (`words`: only words of the sentence itself, as it writes them and in its order), so the result reads "These words sounded a little different: Good, morning". A phrase of Day 2 ("nice to meet you") gets the same. **A sentence's parts are not counted** (that is every vowel in it, by a recogniser that mishears some), though a phrase whose parts a lesson wrote out still is; and nothing is drawn of a sentence, which has no parts to draw.
- **The library's own threshold is set here, once** (`TWO_WRONG_SOUNDS` in `assess/sounds.py`). OpenPronounce reports a word when its wrong sounds add up to two, but never counts a wrong sound as quite a whole one, so two plainly wrong sounds came to 1.99: the app's own voice saying "Good morning" was judged against "Good evening" and passed as right (measured 2026-10-13). It is now two sounds, each nine parts in ten sure. The three Day 2 clips come out as before. **Like every number here it is untuned**; that case is its only evidence.
- **A finding is said, and under that drawn, where the server sent the numbers to draw from** (`FindingLine`; decided 2026-10-13 from reference designs the user brought). The sentence says what to do; the drawing shows what was done, which the sentence leaves out. **Stress:** the word's parts twice, "The word" and "You", the strong one large in each (`StressComparison`). **A part too many or too few:** beats as dots, the word's and those heard (`PartBeats`). **With anything to try come two buttons side by side, "Hear the word" and "Hear yourself"** (`CompareByEar`): the learner's ear is the better judge, and each waits while the other plays.
- **What the references had and this does not, on purpose.** No mistake is pinned to a part or a letter ("silent d", "the extra syllable is this one"): the scorer does not know where in the word a thing happened, so the beats are not the word's parts and none is marked. No target and spoken in phonetic letters: the recogniser's raw output is noisy, and that script means little to a beginner. No pitch in Hz or loudness in dB against a reference: there is no reference voice, by design. No red and green: it would read as pass and fail, and this is a first version that can be wrong; the card stays the soft "something to try" colour. **Adding any of these needs the scorer to know more, and that measured on learners first.**
- **When it cannot be checked** (the scoring service is down, the phone is offline, the browser cannot read back its own recording, too many checks in a minute) the screen says which, and listening to oneself works as before. A browser that cannot make a WAV is not offered the button at all. Checking is never a condition of the day.
- **The service judges a word before it listens, and asks itself one over HTTP once it does** (`warm`, `ask_itself`, with `assess/warm.wav`: the app's own voice saying "hello", a machine's): without both, a learner's first check after a start took 13 seconds; with them, about one.

- **What it is:** `python -m assess clip.wav "Wednesday" --parts "We(d)n(e)s-day" --stress 1` prints findings as **codes with a confidence, never sentences** (`ok`, `nothingHeard`, `extraSyllable`, `missingSyllable`, `stressMoved`, `soundDiffers`), so the app can say them from stored texts in the learner's language. `--parts` and `--stress` are Day 2's `syllables` and `stress`.
- **What it uses:** OpenPronounce's sound recogniser only (`assess/sounds.py`, the one file that touches it; one model of about 1.2 GB, pinned version), Praat through `praat-parselmouth` for stress (GPL: server-side only), and the program espeak-ng for the sounds a word should have. WhisperX and Montreal Forced Aligner were considered and left out: the first writes the word the speaker meant, the second says where sounds are, not whether they were said.
- **Stress is each syllable against the speaker's own others** (length, loudness, pitch; `assess/stress.py`), never against a target voice in Hz. **An Indian accent is not a mistake**: `assess/variants.py` lists the sounds let through (`TODO(content)`: a teacher's review).
- **The bar it has still to be measured against** (it was to be met before a code reached a screen; see above for why it was not): on recordings of our own learners, right at least 8 times in 10 when it speaks, and under about 3 seconds a word. `python evaluate.py recordings/` prints that per code; the recordings do not exist yet, and every weight and margin is an untuned guess until they do. **Until it is met, do not remove the first-version note or widen where findings are shown.** `recordings/` is git-ignored: learners' voices never go in the repository.
- **It has run, and what it costs is measured** (2026-10-13, on the 2-core 8 GB laptop; `speech/README.md` has the table): 1.4 to 1.7 GB of memory and 0.5 to 0.7 seconds a word as OpenPronounce loads its model, which is what the service runs; 1.15 GB and 0.2 to 0.25 seconds as an 8-bit copy, which was measured and is not in the repo (its confidences differ, and nothing has set thresholds for it). Speed clears the bar; **rightness is still unmeasured** (the only clips are a machine's voice). The app is to run on **a small rented server** (decided 2026-10-13), so memory decides what stays loaded: the voices hold 1.5 GB and need not run for learners once the lessons' sounds are made ahead of time (the shelf serves them with the speaking service down).
- **The scorer has an environment of its own, `speech/.venv-assess`**: OpenPronounce cannot be installed beside the voices (it needs an older `click` than their `transformers` allows, and `phonemizer` where Kokoro has a fork under the same name). Nothing is installed on the system for it: espeak-ng comes from `espeakng-loader`, and a WAV needs no `ffmpeg`, which is why the app sends one and never the browser's own webm or mp4.
- **Its own tests** are `pytest` in `speech/` (logic on fixed numbers, no model). ESLint and Prettier ignore the folder. `speech/README.md` has the set-up.
- **Next:** recordings of our own learners, so that the bar can be measured and the thresholds set (`TODO(content)`: theirs to collect; nothing kept by the app can supply them); which sound differed, said in a way a learner can use (`TODO(lessons)`); how strong each part sounded, as bars, from the scorer's own per-part scores, which the server does not pass on yet (`TODO(lessons)`); Days 4 to 7, where the learner speaks in a conversation or at length and how it sounded is not checked (`TODO(lessons)`; in the role-plays the words of a reply can be: "Checking a reply" below). **A word of several words ("nice to meet you") is judged like one word**, which the scorer was not designed around: its stress finding there is the shakiest it gives (`TODO(lessons)`: say less about a phrase, or nothing about its stress).

### Checking a reply (`speech/assess/words.py`, `server/src/modules/conversation/`)

**In a role-play (Days 4, 6 and 7) a learner can have a reply they gave checked: what was heard, whether it answers the partner, and a better way to say it.** Asked for by the user on 2026-10-13, with the models they chose: speech to text, then a small Qwen on our own machine, then the result in the learner's language. It is a first version like the pronunciation check, says so every time with the same note, and **nothing may be built that counts on it being right** (no score, no progress, no lock): it has been measured on written replies and a machine's voice, never on a learner.

- **The path:** a turn the learner answered aloud gets a button under its bubble, "Check my reply" (`ReplyCheck`, for as long as that turn's recording is kept: until the next answer replaces it). On the tap the app sends the recording as a WAV to `POST /api/conversation/replies?partner=&suggested=` (behind `requireVerified`, 10 a minute for each learner) with the partner's line and the lesson's suggested reply. The server has the scoring service write down the words (`/transcribe`: Whisper), has Qwen read them (`grader.ts`, through Ollama's HTTP interface on `GRADER_URL`), and answers `{ heard, fits, better }` (`replyAssessmentSchema`). `ReplyFeedback` says it from stored texts (`lessonDay.reply.*`); what it found stays under its turn after the recording has gone.
- **It is sent on a tap, turn by turn, and kept nowhere**: the same rule as a recorded word. The recording and the words made of it are held in memory while they are judged and are not written down, kept with the account or logged. **Checking every reply by itself, without that tap, is a new decision** (it was not asked for, and the rule in §12 forbids it until it is).
- **The conversation does not wait for it and does not change with it.** The partner's next line follows whatever was said; tapping the button counts as turning to one's own recording, so the microphone then waits for a tap (as after "Listen to yourself"). Day 4 is still scripted, and still says "Talk to {name}", never "AI".
- **The server sends no sentences of its own.** `heard` and `better` are the learner's own English, as heard and as it could be said (shown `lang="en"`); everything said about them is a stored text in the learner's language. There is no runtime translation.
- **Qwen is asked two small things, never "is this right?"** Asked that, it said yes to all 37 test replies. It is asked to **rewrite the sentence as correct English** (a slip is a rewrite that differs, which also gives the better sentence) and, with a reason first, **whether the reply answers what was said**. `judgeReply` (`routes.ts`) holds the rules: the suggested reply itself is right without asking; one word is not corrected; **a rewrite is shown only if it is still the learner's sentence** (`stillTheirs` in `words.ts`: it keeps half their words, adds few, and leaves every name as heard, because the model "corrects" a name it does not know); and **whether it answers is asked of the corrected sentence**, or a grammar slip is taken for a wrong answer.
- **Only a doubt is told about whether a reply answers** ("This may not answer what {name} said"), never praise. The model was set to err towards yes, because refusing a good answer is the costly mistake: on 101 written replies it refused none of the 78 that fitted and missed 9 of the 23 that did not, and on live sound it passed a sentence in Hindi. So its yes is not shown as "that answers"; with no doubt and no better sentence the card says only "We found nothing to change".
- **The better sentence is written, not said.** A sound is kept for good by the server's shelf and the browser, and this one is all but the learner's own words (`TODO(conversation)`: a way to hear it that keeps nothing).
- **What Whisper cannot do, known so far:** it is an English-only model, so **a reply in Bengali or Hindi comes out as nonsense in English letters**, or as nothing; it writes what it takes a speaker to mean, so it may tidy a slip away; and it makes a likely phrase of a silent room, which two checks in `words.py` hold back (`QUIET`, `UNSURE`: untuned guesses). **How it hears our learners' accents is unmeasured** (`TODO(content)`: the same recordings the pronunciation check needs).
- **What it costs** (2-core 8 GB laptop; `speech/README.md` has the tables): Whisper about 0.35 GB more in the scoring service and 1 to 1.7 s a reply; Qwen 1.1 GB (1.35 committed) and 1.5 to 3 s; the first reply after Ollama starts waits 20 to 28 s for the model. A 4-billion Qwen was measured and was no better. **Another model (`GRADER_MODEL`, `WORDS_MODEL`) has to be measured on the same replies before it is used.**
- **When it cannot be checked** (the scoring service or Ollama is down, the phone is offline, too many checks in a minute) the card says so and the button stays to try again. A browser that cannot make a WAV is not offered the button.
- **Running it:** `npm run dev:scorer` (Whisper is loaded with it; without its model the service still starts and judges words) and `npm run dev:grader` (Ollama; where it lives on a machine is in `server/.env`: `OLLAMA_BIN`, `OLLAMA_MODELS`, `OLLAMA_TMPDIR`). Tests: `server/test/replies.test.ts` (a fake listener and grader), `speech/tests/test_words.py`, and Day 4's in `LessonDayPage.test.tsx`.

### Admin-managed settings (runtime config)

Content an admin can change is never hard-coded in components. Settings objects (schemas and hooks all in `shared/lib/appConfig/`, because both the learner screens and the admin editors use them): `landing` (logo, hero image, overlay text, button labels), `languages` (learner languages with flags), `learner-profiles` (a male and a female picture per age group), `screen-texts` (per-language text overrides; schema in `shared/lib/i18n/screenTexts.ts`), `curriculum` (per-language wording of the course; schema in `shared/lib/curriculum/curriculumOverrides.ts`), `week-pictures` (one picture per week, the same in every language; `shared/lib/curriculum/weekPictures.ts`), `week-dialogues` (Day 1's conversation; `shared/lib/curriculum/weekDialogues.ts`), `week-vocabulary` (Day 2's words; `shared/lib/curriculum/weekVocabulary.ts`), `week-sentences` (Day 3's sentences to translate; `shared/lib/curriculum/weekSentences.ts`), `week-roleplays` (Day 4's role-play; `shared/lib/curriculum/weekRoleplays.ts`), `week-challenges` (Day 5's challenge; `shared/lib/curriculum/weekChallenges.ts`), and Day 6's three: `week-quizzes` (the review's quiz; `shared/lib/curriculum/weekQuizzes.ts`), `week-review-dialogues` and `week-review-roleplays` (the review's own conversation and role-play, stored like Day 1's and Day 4's; `shared/lib/curriculum/weekReviews.ts`), and `week-scenarios` (Day 7's scenarios; `shared/lib/curriculum/weekScenarios.ts`). The pattern:

- One Zod schema per settings object. Build it from `appConfig/fields` (`assetUrl`, `text`, `optionalText`, `languageTag`, `section`). **Every field has a default** (`.catch(default)`), so an empty, partial or partly invalid value still yields a complete config. For lists, keep the valid entries and fall back to the default list only when none are usable.
- A link to a video or sound uses `mediaUrl`: an `https:` URL or a root-relative path, never a `data:` URL (media does not fit in browser storage, so it is linked, not uploaded).
- Image fields use `assetUrl`: `https:` URLs, root-relative paths, or uploaded raster `data:image/(png|jpeg|webp)` URLs. Never SVG data URLs or other schemes. Settings text is rendered as plain text, never HTML. Images from settings need an `onError` fallback.
- **Storage.** `settingsRepository` (`appConfig/settingsRepository.ts`) keeps settings in this browser's `localStorage` and notifies subscribers in every tab; nothing else may touch settings storage. **For the ten `week-…` objects that storage is a copy of the server** (see "Lesson content" under Backend): `weekContentRemote.ts` fills it and sends an editor's save. For the others (`landing`, `languages`, `learner-profiles`, `screen-texts`, `curriculum`) it is still all there is: an admin's edit is that browser's alone (`TODO(backend)`: `GET/PUT /api/app-config/<name>`).
- Read with `useAppConfig({ name, schema, defaults })`, wrapped in a small `use<Name>Config()` hook. It is synchronous and live: defaults until an admin saves, then every open screen re-renders on each save. Screens never show a loading state for settings.
- Button destinations and behaviour stay in code (`paths`); settings carry content only.
- The installed-app icon, name and splash color come from the build-time web manifest and are **not** runtime-configurable.

### Screen texts and languages

The whole app is shown in the language the learner chose. They can choose it in four places: first on the landing page ("Choose the language you learn in": a `ChoiceChips` of the languages by their own names, saved on the tap), then the language picker on the account screen (`AuthLanguageSelect`), the onboarding language step, and afterwards Profile › Language (`LanguageSetting`, which saves on the tap like the theme does); all save to the same `useLanguageStore`, so **a choice made on the landing page is the language of the account screen and of every step of onboarding**, and is pre-selected on the language step. Nothing is ticked on the landing page for a visitor who has not chosen: the app is not put into a language nobody picked. The language step and Profile list the languages with `LanguageChoiceList`. Until they choose, everything is English. There is no runtime machine translation: every text is a stored text.

- Catalogs live in `shared/lib/i18n/`: `en.ts` is the source of truth for keys; `bn.ts` and `hi.ts` are typed `TextCatalog`, so **adding a key to `en.ts` requires it in `bn.ts` and `hi.ts` too** (compile error otherwise). Bengali and Hindi were written by the assistant and still need a native speaker's review.
- In components call `const t = useT()` and then `t('key')`. **Never call it at module scope** and never keep translated strings in module-level constants: keep the key (see `ageGroups.ts`, `themes.ts`) and translate while rendering. There is deliberately no global `t`.
- Lookup order for a key: admin's text for the language → built-in text for the language → admin's English → built-in English. A regional code (`bn-IN`) falls back to its base (`bn`). A language the admin adds has no texts until they are entered under Admin › Screen texts; it shows English meanwhile.
- The learner's language is `useLanguageStore().language` (`null` until chosen → English). `AppLanguageProvider` applies it app-wide and keeps `<html lang>` in sync. `I18nProvider` can be nested to show part of a screen in another language (the language step previews the highlighted language this way) — wrap that part in an element with the matching `lang`.
- Use `isEnglish(language)` when behaviour depends on the learner having a mother tongue (e.g. the placement intro hides "Translate" for English-only learners).
- The **landing page's own wording is not translated per learner**: it is content in the `landing` settings (brand, tagline, button labels), written once. Its headline is instead written once per language (`overlay.headlines`, up to 8). Until a visitor has chosen a language `HeadlineSlider` rotates through them: every 5 seconds the current one slides out to the left and the next slides in from the right. **Choosing a language in the picker under it slides to that language's headline and ends the rotation** (the English headline for a language that has none, else the first); that picker is the control that stops the moving text, so it is always there, and it lists the `languages` settings, not the headlines' languages. Only the picker's own heading is a screen text (`landing.language`), so it reads in the language just chosen; `TODO(content)`: the button labels stay as the admin wrote them, in one language.
- New text keys should get a home in `features/admin/lib/textGroups.ts` so they are grouped by screen in the editor (unlisted keys still appear, under "Other"). Admin › Screen texts has a "Screen" picker built from those groups, so an admin can show one screen's texts at a time; guidance for a whole group goes in `adminText.texts.groupNotes`.

### The journey (Home) and the bottom navigation

- **The course** is 50 weeks in 10 sections of 5 (`shared/lib/curriculum`). `curriculum.ts` holds the structure; `texts/en.ts`, `bn.ts`, `hi.ts` hold the wording (section names and, per week, a goal, a real-life context and a communication challenge), and `texts/enOutcomes.ts`, `bnOutcomes.ts`, `hiOutcomes.ts` hold each week's five outcomes (what the learner will be able to do; the fifth sums the week up). It is content, not screen text: it is **not** in the i18n catalogs or in Admin › Screen texts; it has its own editor, Admin › Curriculum. `useCurriculum()` gives it in the learner's language, falling back to English. Bengali and Hindi were written by the assistant (`TODO(content)`: native review); Hindi goals use "मुझे … आता है" so they do not depend on the learner's gender; outcomes are verbal nouns in Bengali ("… করা") and infinitives in Hindi ("… करना") for the same reason. The outcomes were written by the assistant in all three languages, except Week 20's English, which is the design's (`TODO(content)`: expert review). Section names 1–5 come from the design, 6–10 were written to match.
- **Every text of the course has a key** (`CurriculumKey`: `section.4`, `week.16.goal`, `week.16.context`, `week.16.challenge`, `week.16.outcome.1` to `.5`; 410 in all). An admin's wording is stored per language under those keys in the `curriculum` settings — only what they changed, like screen texts — and looked up the same way: admin's text for the language → built-in text for the language → admin's English → built-in English (`curriculumText`). **The structure is not editable**: sections and weeks cannot be added, removed or reordered, because Home, the routes and placement count on 10 × 5.
- **Admin › Curriculum** (`CurriculumPage`) edits one section at a time: a language, a section, then the section's name and its five weeks (`CurriculumWeekSection`: the three-line summary, then the weekly overview's picture and five outcomes). It holds two drafts, the wording and the pictures, behind one Save bar. Outside English each field shows the English it is written from. Change overrides only through `withCurriculumText`, which keeps them in the schema's order so an undone edit leaves nothing to save.
- **The tutor on a screen** (`TutorNarrator` in `shared/lib/tutor`, drawing `TutorBar` from `shared/ui`): the learner's chosen face in a fixed place at the top — large (112px) and centred in a row of its own, so that someone is felt to be there — with **one line about what matters on that screen right now** written in a speech bubble under it and said aloud — never the whole list. So far on the journey screens: Home ("You are in Section 1, …. Tap it to see your weeks."), a section (this week and its situation, or which weeks it holds), and a week's overview (the day that is next, naming the pinned button by its own label; praise and a thumbs up once the week is done). **A further screen gets the tutor by rendering `TutorNarrator` with its line**; lesson days and the other tabs do not have it yet, because lessons speak themselves and the tutor must not talk over them (`TODO(lessons)`).
- **Its lines are stored screen texts** (`tutorSays.*`, with `{placeholders}` filled from the course and the screen), in the language the app is shown in and editable under Admin › Screen texts — not generated, which is why the bar is "Your tutor" and never "AI" (`TODO(backend)`: a tutor that answers). Bengali and Hindi were written by the assistant (`TODO(content)`).
- **The tutor speaks by itself** when a screen opens and when its line changes (`useTutorNarration`), in the tutor's voice for that language, lips moving (`useLipSync`). Three things keep it silent, and the line is written in every case: the learner **muted** it (the speaker button on the bar; remembered in this browser by `useTutorSoundStore`), there is **no voice for the language** (one an admin added, or any language while the server's voices cannot be loaded — the line is never said in another language's voice, **nor said in English instead: the tutor speaks the language its line is written in, and what is heard is what is read**; the bar then has no buttons), or the learner **has not touched the page yet** since it was opened (`navigator.userActivation`; browsers allow no sound before that). The face is a button that says the line again, or stops it; unmuting says it at once. A line that cannot start is no error.
- **Where it sits:** on a screen that scrolls as a whole (Home, a section) it is the first element and sticks to the top (`JourneyTutor` in `features/home/components`, the `sticky-screen-top` utility), so the list scrolls under it; on a `StepScreen` it goes in the `topBar` slot, which never scrolls. The mouth's movement is kept inside `TutorNarrator`, so the screen around it does not re-render with it.
- **The part that stays is a band of its own colour** (`bg-primary-soft`, in every theme), from edge to edge and over the notch, ending in a straight edge with a soft shadow: where the fixed part stops and the list begins can be seen. `TutorBar` is drawn as a panel of that colour; `JourneyTutor` runs it to the screen's edges, and a week's overview makes its whole top bar the band (`StepScreen`'s `topBarTone="soft"`), and so does a role-play, with the partner in the tutor's place (`PartnerBand`: see "Day 4's screen"). Controls in the band use the variant drawn for it (`IconButton` `secondary`).
- **The tutor is in exactly the same place on every screen that has it**: first in the band, with `TutorBar`'s own padding above it, so the face does not move as the learner goes from Home to a section to a week, or on into a role-play. Anything else a screen keeps fixed goes **under** the tutor's rows, never above them: a role-play has the day's place in the week there (the bar, "‹ Day 3" and "4/7"), and a week's overview has a third row there, the bar for its place in the course, alone (an arrow beside a bar reads as moving the bar, so there is none: another week is reached from its section's list, or by the pinned button once this one is done). A `StepScreen` band adds no padding of its own for this reason.
- **The way back sits in the band's first row, top left, and so never scrolls away**: `TutorBar`'s `leading` slot, opposite the mute button with the face centred between them, on a section and on a week alike; a role-play's band lays its back arrow over the same corner.
- **Home** (`features/home`) lists the ten sections (`SectionCard`); a section opens its five weeks (`WeekCard`) at `/home/sections/:section`, and a week's card opens its overview. No section or week is locked. An unknown section or week number is a 404, checked in the route's loader.
- **A week's overview** (`WeekPage`, `/home/weeks/:week`) is a `StepScreen` without the bottom navigation: in its band, back to the week's section, the tutor, and a bar for the week's place in the course; then "Week 20 of 50"; the heading "Real-life situation" over the week's situation (the same text as on its card); the week's picture (`WeekPicture`; a drawn stand-in until an admin uploads one, and if it fails to load); the five outcomes (`OutcomeList`: ticks as designed, in a list named "What you will be able to do" so they are not read as work already done); and "Start Day 1" pinned in the thumb zone.
- **The overview's button opens the first day not finished in that week** ("Start Day 1", then "Start Day 2", …): `nextLessonDay` over `useLessonProgressStore` (`shared/lib/learner/lessonProgress.ts`), which remembers the days done per week in this browser. Nothing is time-locked. Once all seven are done the button leads on to the next week instead (see Day 7 below). A finished day cannot be reopened from the overview yet (`TODO(lessons)`: a list of the week's days); from inside a day, the day before can (see "‹ Day 1" under Lessons).

### Lessons: one shared screen per day

- **Every day is one screen shared by all 50 weeks; only its content differs per week.** This is the rule for any day added or reworked: one route (`/lessons/weeks/:week/days/:day` → `LessonDayPage`, a full-bleed `StepScreen`), one step component per day, content keyed by week number in its own settings object with any built-in content beside it in `shared/lib/curriculum/`, and an editor under Admin › Lessons. Never a per-week component. A day not built yet, or a week without that day's content, shows `LessonNotice` ("coming soon").
- **A week is seven days** (`DAYS_PER_WEEK`: five core, two flexible). Built: **Day 1 "Watch and listen"**, **Day 2 "Learn useful words"**, **Day 3 "Translate and speak"**, **Day 4, a role-play ("Talk to …")**, **Day 5, the week's challenge** — all five core days — and the two flexible days, **Day 6, the week's review** and **Day 7, the real-world challenge** — with content for Weeks 1 to 15 so far, which is Sections 1 to 3 (`TODO(content)`: weeks 16 to 50). **A week's content is kept in the database** (see "Lesson content" under Backend): Week 1's is also built into the app as its offline fallback, and the weeks after it exist only as files that are imported (`server/content/week-02.json` and on; "Writing a week from the syllabus" there says how they are written). The top of each day (`LessonTopBar`) has back to the week, a bar and "2/7": the day's place in the week, not a step inside the day. The bar, the count and the way back a day are `LessonDayProgress`, which a role-play draws in its band instead (below).
- **Every day after the first has a way back to the day before, to go through it again**: "‹ Day 1" in `LessonTopBar`, between the bar and the count (an outline `Button` of size `sm`, named "Go back to Day 1"). It is on the day's own screen only — inside a part of it (a review activity, a challenge under way) the back arrow leads to the day and there is no second way out — and within the week only: Day 1's way back is the week's overview. A day opened this way is not locked again if it was finished, and finishing it again changes nothing; "Next" returns to the week, whose button still opens the first day not done. The top bar works out the link from the route's week, so no day's screen passes it.
- **Finishing a day** ("Next", `LessonNextButton`) records it in `useLessonProgressStore` and goes back to the week's overview, whose button then opens the next day. While "Next" is locked it says why, right above itself. What a day requires is listening (Days 1 and 2), seeing the answer (Day 3), reaching the end of the conversation (Day 4, where every turn can be skipped) one attempt at the challenge (Day 5, with "I can't record right now" beside it) any one part of the review (Day 6) or one scenario taken to its end (Day 7), both of which can also be skipped — never speaking, and never anything a device cannot do: a device that cannot play the content is told so and may go on. A day finished once is not locked again.
- **Day 1's content: one conversation per week** (`WeekDialogue` in `shared/lib/curriculum/weekDialogues.ts`): lines of `speaker`, English `text` and `translations` by language, plus an optional `videoUrl` and optional `voices`: which of the speakers is a woman and which a man, by the name beside their lines (`{ Asha: 'female', Ravi: 'male' }`; only names that speak are kept, in the order they first speak). Week 1 is built in (`dialogues/week1.ts`, written by the assistant with its Bengali and Hindi; `TODO(content)`: review). An admin's conversation for a week replaces the built-in one whole; only weeks they wrote are stored. `useWeekDialogue(week)` gives the one in force, or `null`.
- **Day 1's screen** (`WatchAndListenStep`): the media, then the conversation written out (`DialogueLines`). Speaker names and lines are English content, marked `lang="en"`.
- **Media** (`ConversationMedia`): with no video, the week's picture (`ScenePicture`) under a play/stop button, while the lines are said — each speaker in a voice of their own — with "Play slowly" and a bar of lines played. With a video link, a native `<video controls>` takes their place; it has no caption track (the conversation is written out right below; `TODO(content)`: caption files), and if it cannot load, the voice takes over.
- **A person in a conversation is read in a voice that fits them, not in the learner's tutor's**: a speaker the content calls a woman or a man gets the **default voice of that kind** (`SpeechPart.voice`), whoever the learner's tutor is and whatever voices they chose in Voice settings, so "Asha" is never read by a man because she speaks first. Only a speaker the content says nothing about falls back to the tutors' voices by turn (the first speaker the learner's tutor's, the second the other's). Week 1's conversation and its review's both say it; an admin sets it under Admin › Lessons ("Voices"). **The role-play partner (Days 4, 6 and 7) is the other case, and the opposite one: it is played by the learner's own tutor**, face and voice (see "Day 4's screen").
- **Dialogue and Transcript:** Dialogue is the English, each line with a button to hear it again. Transcript adds the learner's language under each line and has no buttons. The tabs appear only for a learner with a mother tongue the conversation is translated into.
- **Day 1's "Next" opens after one full listen** (the voice to the last line, or the video to its end), and stays open for that week afterwards. Stopping part-way, or hearing single lines again, does not count.
- **Day 2's content: the week's words** (`WeekVocabulary` in `shared/lib/curriculum/weekVocabulary.ts`): up to 8 entries of `word` (English), `phonetic` spelling, an optional square `imageUrl` and `meanings` by language, plus how it is said (next bullet). Week 1's six are built in (`vocabulary/week1.ts`: the words its conversation uses, written by the assistant; no pictures ship with them). Stored and resolved exactly like the conversations; `useWeekVocabulary(week)`.
- **How a word is said is content too, and all of it optional**: `syllables` (the word in the parts it is said in, **each as it is spelled**, with letters that are not said in brackets: "We(d)n(e)s", "day"), `stress` (which part is the strong one, from 1; `null` for none, as in a word of one part) and `tips` by language (up to 3 each, `en` the fallback: Day 3's shape, read with `wordTips`). **The parts must spell the word** (`syllablesSpell`, brackets, hyphens and spaces aside): parts that do not are dropped by the schema and refused by the editor, so a reworded word cannot keep another word's parts. A respelling ("WENZ-day") is therefore not accepted; how it sounds is the `phonetic` field's job. Week 1's were written by the assistant in all three languages (`TODO(content)`: review).
- **Day 2's screen** (`LearnWordsStep`): a two-column grid of `WordCard`s — picture (or the word's first letter), word, phonetic spelling, and its meaning for a learner with a mother tongue. Tapping a card says the word, ticks it as heard and makes it the one to practise. A word cut short by the next tap is not heard. The phonetic spelling is hidden from screen readers, which get the word and its meaning. Above the grid a `SegmentedControl` sets the speed every word is said at (Normal · Slowly, `SLOW_RATE`; gone on a device that cannot speak); under it `TipsCard` ("How to say it") shows the selected word's tips, in the learner's language or else English. "Next" opens once every word has been heard, at either speed.
- **The word being practised is shown in its parts** (`SyllableLine`, inside `PronunciationPractice` in place of the plain word, when the word has `syllables`): the parts side by side, the strong one larger, filled and with "Strong" written under it (never size or colour alone), silent letters crossed out with "Crossed-out letters are not said" under the row. A screen reader gets the word whole, the parts as a list, and the silent letters named after that note (the crossed-out letters themselves are hidden from it). **It teaches and judges nothing itself.** What was found in a recording is shown apart from it, in `PronunciationFeedback`: there the same row of parts is drawn twice to show where the stress was put (`StressComparison`, through this component's `label` and `withoutSilentNote`), never on the row the learner practises from. A word without parts is shown as before.
- **Practising pronunciation** (`PronunciationPractice`, pinned above "Next" with it): the learner says the selected word into `MicButton` and can play the recording back. Nothing is kept: the take lives in memory and is dropped when another word is chosen or the screen goes. **On Day 2 a take can be checked by the server, on the learner's tap** ("Check how I said it", under the panel; what was found appears in the screen's content, brought into view): a first version that says so every time (see "Speech scoring"). The panel itself, which Days 3 and 5 also use, still rates nothing. The panel says the microphone will be asked for before the first tap; a blocked microphone shows `MicrophoneHelp` and never blocks the day.
- **Day 3's content: the week's sentences** (`WeekSentences` in `shared/lib/curriculum/weekSentences.ts`): up to 6 entries of `english` (the answer), `alsoAccepted` (up to 4 other English sentences that are just as right), `translations` by language (what the learner translates from) and `tips` by language (up to 3 each; `en` is what other languages fall back to). Week 1's five are built in (`sentences/week1.ts`: lines of its conversation, written by the assistant; `TODO(content)`: review). Stored and resolved exactly like the conversations; `useWeekSentences(week)`. Built-in content lists its languages in the order the schema stores them (bn, en, hi), or an undone edit would leave something to save.
- **Day 3's screen** (`TranslateAndSpeakStep`): **one sentence at a time** — "Sentence 2 of 5" in the eyebrow, the sentence in the learner's language (`SentenceCard`), a field for the English (`TranslationForm`), the say-it panel, then the tips (`TipsCard`, always visible, in the learner's language or else English). "Next" moves to the following sentence and, on the last, finishes the day. When the sentence changes, focus moves to the heading so it is announced, and what was typed, shown and recorded is forgotten.
- **Checking a translation is a plain comparison in the browser** (`features/lessons/lib/matchAnswer.ts`): the typed text against the answer and the other accepted sentences, ignoring capitals, punctuation and short forms ("I'm" = "I am"). A match gets a tick and "That is right"; **anything else is set beside the answer to compare, never called wrong**, because a right sentence the admin did not list cannot be recognised (`TODO(backend)`: let the server judge). One button does both jobs: "Check" once something is typed, "Show answer" while nothing is. "Next" opens once the English answer is on show, either way.
- **A learner with nothing to translate from** (English chosen, or a sentence not written in their language) gets the English sentence itself to listen to and say, with nothing locked.
- **The speaker beside a sentence in the learner's language** is shown only when there is a voice for that language (`useVoiceAvailable`): Bengali and Hindi have one, a language an admin added does not. The English answer's speaker is there whenever the app can speak at all.
- **Saying the sentence** reuses `PronunciationPractice` (given a `title`, without the word line) inside the content, under the field; `useSpokenPractice` (`features/lessons/hooks`) is the recording wiring Days 2 and 3 share. Optional, like Day 2, and like Day 2 a recording can be checked by the server on a tap (`PronunciationFeedback` with `kind="sentence"`: see "Speech scoring"). **Only a recording made with the English on show can be checked**: before that the learner may have said another sentence, and a right one, and it is the shown one it would be held against. A take from before gets one line under the panel instead of the button ("say the sentence once more now that you can see it").
- **Day 4's content: one role-play per week** (`WeekRoleplay` in `shared/lib/curriculum/weekRoleplays.ts`): a `partner` (as it reads after "Talk to": "Ravi", "the barista"), optionally their name when the tutor who plays them is of the other kind (`asWoman`, `asMan`: see "The partner is called…" below), an optional square `imageUrl`, and up to 8 `turns` of the `partner`'s line, a suggested `reply` (both English) and `cues` by language (what to say, told without the English words). Week 1's five turns are built in (`roleplays/week1.ts`: the week's conversation with the learner in Asha's place, written by the assistant; `TODO(content)`: review). Stored and resolved exactly like the conversations; `useWeekRoleplay(week)`.
- **The partner is played by the learner's tutor: the face they chose, speaking in that tutor's English voice** (decided by the user on 2026-10-13; `TutorAsPartner`, lips moving with the line through `useLipSync`). The voice was the tutor's already; with a stand-in figure and a name of the content's above it, a learner whose tutor is a woman heard "Ravi" speak as one. Now the voice has the face it belongs to: a woman's tutor, a woman's voice (the one chosen for her in Voice settings, else English's default female voice), and a man's likewise. A picture an admin uploaded for a partner is still shown in the tutor's place.
- **The partner is called what fits the tutor who plays them** (decided by the user on 2026-10-13: "make it contextual"). A role-play keeps the name it was written with (`partner`) and may give another for the other kind of tutor (`asWoman`, `asMan`): Ravi is Asha when a woman plays him; Meera is Mohan, Priya is Rahul and Anita is Anil when a man does; Sam and "the barista" are themselves either way. `roleplayPlayedBy(roleplay, kind)` puts the fitting name in the heading and **wherever a line or a suggested reply says the written name, as a whole word** ("My name is Asha"), and `RolePlayStep` plays that; the review's list names them the same way (`partnerNameFor`). The cues in the learner's language name nobody, by design, so they need no change. An admin writes both under Admin › Lessons ("Name when the tutor is a woman / a man"); left empty, the written name holds. The names were chosen by the assistant (`TODO(content)`: review). **A new role-play whose partner has a woman's or a man's name needs the other one**, or one kind of tutor will speak under the wrong name.
- **Day 4 is scripted, and says so by not saying "AI".** The partner does not listen: it says the next written line whatever the learner said, and the title is "Talk to {name}", never "(AI)". What the learner said is looked at only when they ask, a reply at a time and after the fact (see "Checking a reply" above); the conversation neither waits for that nor changes with it. `useRolePlay` (`features/lessons/hooks`) is the only place that knows the script; a partner that listens and answers replaces it later (`TODO(backend)`), and the "(AI)" label and "Listening…" wording come back only then.
- **A role-play keeps its partner in view** (asked for by the user on 2026-10-13, to match the week's overview; they chose that screen's order over pinning the rows as they were). The top of `RolePlayStep` is a band in the soft primary colour that does not scroll (`PartnerBand` in `StepScreen`'s `topBarTone="soft"`): **the partner's face first** (`PartnerAvatar`: the learner's tutor, or an admin's picture), where the tutor's is on the week's overview and padded like it; the way back laid over the start of that row; and under it the day's place in the week (`LessonDayProgress`). "Talk to {name}" and the conversation scroll under the band, and the face stays put through all three stages. It has no speech bubble and no mute button: the partner's lines are the conversation, each with a button to hear it again. The other lesson days keep their plain top bar, having nobody in it.
- **Day 4's screen** (`RolePlayStep`) has three stages. _Intro:_ the partner in the band, the microphone note, and "Start the conversation" — nothing speaks or asks for the microphone before that tap. _Talking:_ the conversation as a chat (`TalkTranscript`, announced as it grows) over pinned controls (`TalkControls`: a status line with the seconds running out beside it, Hint · the microphone · End chat, and "Skip this turn"; time that ticks is kept out of the announced line, which says each state once). _Done:_ "Well done", "Practise again" and "Next", which finishes the day.
- **A turn:** the partner's line is said aloud; the learner speaks, and when they have finished **the partner's next line follows by itself**. "Skip this turn" does the same without the microphone, so speaking is never a condition. A stop before any sound was captured (the microphone was still opening, or is blocked) moves nothing.
- **Turns are taken without tapping where the device allows it** (`turnTiming` in `features/lessons/lib`, applied by `useRolePlay`; the times are fixed in code). When the partner's line ends the microphone opens by itself, with **5 seconds** counted down to begin (`TurnCountdown`, beside the status line); nothing said in that time shuts it, the turn stays open and waits for a tap. Once a voice is heard the countdown goes, and **a pause of 3 seconds is the learner's answer**. A turn runs **2 minutes at most**: its last 20 seconds are counted down, then it ends and the partner goes on. A tapped microphone follows the same rules, and a tap on it still ends the turn at once.
- **The microphone opens by itself only once the browser has already allowed it** (`microphoneAllowed`): it is never asked for without a tap, so a learner's very first turn is a tap. Nor does it open by itself after a microphone problem, while "End chat" is asking, after the learner turned to their own recording, or on a device that cannot tell whether anyone is speaking (`canListenForVoice`) — there every turn is tapped, as before, with only the 2-minute limit. The intro says both things before they happen (`lessonDay.talk.autoMic`).
- **"Speaking" is only sound louder than the room** (`voiceActivity.ts`, see §7): nothing is recognised. A loud room may hide a pause (a tap or the limit then ends the turn) and a very quiet voice may not be heard. **The partner's line after a pause or the limit starts from a timer, not a tap**; if a browser refuses that (iOS is the one to check on a real phone), the line is still written out, the "cannot say the lines aloud" notice shows, and the turn waits for a tap.
- **The learner's side of the conversation carries their own picture, small and still** (`LearnerPicture` beside "You could say" and "What to say"; asked for by the user on 2026-10-13): their own photo, else their Google account's, else a plain figure — never the turning coin of Profile, which is neither still nor theirs. Which picture is theirs is one rule, `useLearnerPicture` (`shared/lib/learner`), which Profile uses too.
- **The learner's own words are not shown in their bubble, because they are not known unless they ask.** Once a turn is over its bubble shows the suggested reply under "You could say", with a button to hear it; that turn's bubble also has "Listen to yourself" until another answer replaces the recording — a microphone that opened and shut with nothing said leaves it there. Listening to it closes an open microphone. Only one take exists at a time, as on Days 2 and 3. **Under the bubble, for as long as that take is kept, is "Check my reply"** (`ReplyCheck`): what it heard and found is shown there, apart from the suggested reply, and stays after the take has gone. A skipped turn has nothing to check.
- **The hint has two steps** on the turn being answered: first the cue in the learner's language, then ("More help") the English reply with a button to hear it. A learner with no mother tongue, or a turn with no cue in theirs, gets the English at once. Each turn starts without help.
- **"End chat" asks first** (`EndChatConfirm`, inline where the controls were — there is no sheet or dialog component yet), with staying as the main action; leaving goes back to the week and does not finish the day. The screen is kept awake while turns are being taken (`useWakeLock`).
- **Day 5's content: one challenge per week** (`WeekChallenge` in `shared/lib/curriculum/weekChallenges.ts`): a `title`, an optional `instruction` and up to 6 `tasks` — each a `ChallengeText`, written in English with `translations` by language — and up to 6 English `phrases` as help. Unlike the days before it, **its texts are instructions, not English to practise, so the learner reads them in their own language** (`challengeText`: theirs if written, else English, with the language for `lang`). Week 1's is built in (`challenges/week1.ts`, written by the assistant; `TODO(content)`: review). Stored and resolved exactly like the conversations; `useWeekChallenge(week)`.
- **Day 5's screen** (`ChallengeStep`): the week's own picture (the one from Curriculum, a little lower than 16:9), then "What to do" (`TaskChecklist`), with the recording panel pinned above "Next" (`PronunciationPractice` again, titled "Record your attempt", showing the time against its limit). **One take for the whole task**, up to 2 minutes (`MAX_CHALLENGE_TAKE_MS`; it lives in memory, and is given to the recorder as its limit, whose own default is 30 seconds), ended by the screen when the limit is reached; recording again replaces it.
- **Nothing is submitted or assessed, and the screen says so** (`TODO(backend)`). The mockup's "Submit" is "Next", and its ready-ticked list is the learner's own check: the tasks are a plain list with empty circles until a recording exists, then become tick boxes with "Listen to your recording and tick what you managed" and "Only you can hear this recording. It is not saved, sent or scored." Ticks are never required and are cleared by a new take.
- **Day 5's "Next" opens after one attempt** — or on "I can't record right now" (under the tasks, shown while "Next" is locked), or by itself when the microphone is blocked. It does not wait for listening back or for ticks.
- **Help on Day 5 is asked for, never shown**: "I need help" (`PhraseHelp`) opens the week's phrases, each with a button to hear it; using it changes nothing else. The buttons go while a recording is under way, so the app's own voice does not end up in the take. A week without phrases has no help button.
- **Day 6 is the week's review, and it is optional** (`ReviewDay`, in `features/lessons/components`): a list of up to five things to practise (`ReviewMenu`, under a medal and "Optional day"), each a row that opens it and is ticked once done. The parts, in the design's order, are `REVIEW_PARTS` in `shared/lib/curriculum/weekReviews.ts`: quiz, listening, speaking, flashcards, roleplay.
- **Three parts have content of their own, two repeat the week.** The quiz (`WeekQuiz`, `weekQuizzes.ts`), a second conversation to listen to and a second, shorter role-play (`weekReviews.ts`: the types, schemas and editors of Days 1 and 4, under their own settings names) are written per week; "Speaking practice" is Day 5's challenge again and "Vocabulary flashcards" are Day 2's words, so nothing is written twice. Week 1's quiz, conversation and role-play are built in (`quizzes/week1.ts`, `reviews/week1.ts`, written by the assistant; `TODO(content)`: review). **A part the week has nothing for is left off the list**; a week with nothing for any part shows "coming soon".
- **Three of the five parts are the screens of earlier days**, opened with other content and a back arrow to the list: listening is `WatchAndListenStep` (given its own `title` / `subtitle`), speaking is `ChallengeStep`, the mini role-play is `RolePlayStep` (whose "End chat" then says it can be started again from the review). Only the quiz and the flashcards are screens of their own. Never copy a day's screen for the review: pass it content.
- **Which part is open is in the address** (`?part=quiz`), so the phone's Back closes it and a part can be linked to; an unknown part, or one the week has nothing for, is the list. Finishing a part records it (`reviewParts` in `useLessonProgressStore`, per week) and returns to the list, replacing the history entry. A part done is not a day done.
- **The list's two buttons keep their places** (`OptionalDayActions`, shared with Day 7). The upper one leads on to the first part not done yet ("Start practice", then "Continue practice"; gone when all are done). The lower one leaves: **"Skip this day" before anything is done, "Next" once any one part is** — both finish the day, because it is optional.
- **The quick quiz** (`QuizStep`, `useQuiz`): one question at a time, read in the learner's language like Day 5's texts (`challengeText`; the question is an instruction), answered by picking an English choice (`ChoiceList`) and tapping "Check", which needs a choice and says so. A right answer gets a tick; a wrong one is shown the answer, with a button to hear it (`QuizFeedback`), and **comes back once after the others — never a third time**. The end says how many were right the first time. A multiple-choice answer is certain, so this is the one place a lesson says "not quite"; Day 3's rule (never call a typed sentence wrong) stands.
- **A question is `question` (a `ChallengeText`), `answer` and `others`** (1 to 3, none saying the same as the answer or as each other): the right choice is written apart from the rest, not as a position, so reordering lines cannot change it. Its place among the choices is worked out by `quizChoices` (`features/lessons/lib/quiz.ts`) from the question and the turn — no chance involved, so a render is repeatable.
- **The flashcards** (`FlashcardsStep`, `Flashcard`): the week's words one at a time, from the meaning in the learner's language (and the picture) to the English. "Show the word" turns the card and says the word in the same tap; then the learner sorts it themselves — "I know it" puts it away, "Practise again" sends it to the back of the pile — and the pile is done when it is empty. Nothing is rated. A learner with no meaning to start from gets the English at once, to hear and say.
- **"Adaptive" on Day 6 means only this**: missed quiz questions return, and cards not known yet stay in the pile. Choosing what to revise from the learner's history needs a server (`TODO(backend)`).
- **Day 7 is the week's real-world challenge, and it is optional too** (`ExtendDay`): the week's conversation in other places. The learner picks a scenario and a level (`ScenarioPicker`: the week's picture, then two groups of `ChoiceChips`), and "Start challenge" opens it.
- **A scenario is a name and a role-play** (`ChallengeScenario` in `shared/lib/curriculum/weekScenarios.ts`: `name`, a `ChallengeText` read in the learner's language, and `roleplay`, a `WeekRoleplay` exactly as on Day 4). Up to 3 per week (`MAX_SCENARIOS`). Week 1's three are built in (`scenarios/week1.ts`, written by the assistant; `TODO(content)`: review). Stored and resolved exactly like the conversations; `useWeekScenarios(week)`.
- **The challenge is Day 4's screen** (`RolePlayStep`) given the scenario's role-play, with the scenario and the level above the heading. It is scripted like Day 4 and says "Talk to {name}", never "AI"; the mockup's "open-ended conversation" needs a server (`TODO(backend)`).
- **The three levels are amounts of help, not content** (`CHALLENGE_LEVELS`, fixed in code like the age groups): the same lines at every level, so nothing is written per level. They map to `RolePlayHelp` in `useRolePlay`: **Easier** = `shown` (what to say is there from the start of every turn — the cue in the learner's language, or the English reply where there is no cue — with the English one "More help" away), **Standard** = `asked` (Day 4's behaviour, and what an unknown level falls back to), **Harder** = `none` (no hint button at all; a reply is shown only once the turn is over, as always). Skipping a turn stays possible at every level.
- **Which challenge is open is in the address** (`?scenario=2&level=easier`, scenarios numbered from 1), so the phone's Back closes it; a scenario the week does not have is the picker. Taking a scenario to its end records its place (`scenariosDone` in `useLessonProgressStore`, per week) and returns to the picker, where it is ticked, the first scenario not taken yet is chosen, and the level chosen is still chosen. "Skip this day" before any is done, "Next" after one, as on Day 6.
- **A week is complete when all seven days are done** (`isWeekDone`; a skipped optional day counts). Its overview then says so and its button leads to the next week ("Go to Week 2"; from Week 50, back to the journey) instead of looping to "Start Day 1".
- **Speaking several lines in a row** goes through `speakAll` (`shared/lib/audio/speech.ts`), which hands every line to the device inside the one tap, as iOS requires. `cancelSpeech` settles a playback as cancelled itself, because browsers disagree on the event a cancelled utterance fires.
- **Admin › Lessons** (`LessonsPage`): pick a week and a day, then fill that day for that week, writing one learner language's translations at a time. Day 1 (`DialogueEditor`): the conversation line by line (speaker, English, translation), reorder or remove lines, a voice for each name that speaks (By turn · Female · Male; it belongs to the name and goes when nobody speaks under it), and an optional video link. Day 2 (`VocabularyEditor`): the words (word, phonetic spelling, meaning, picture, and in `WordSoundFields` how it is said: the parts in one field with hyphens between them and brackets around silent letters, "We(d)n(e)s-day", the strong part picked from them, tips in English and in the language being written one per line), reorder or remove; parts that do not spell their word block saving, and a strong part that is taken away is unchosen. Day 3 (`SentencesEditor`): the sentences (the English answer, the sentence in the language being written, other accepted answers one per line, tips in English and in that language one per line), reorder or remove; a one-per-line field is cut to its limits as it is typed, like `maxLength`. Day 4 (`RoleplayEditor`): the partner's name, their name when the tutor who plays them is a woman and when a man, and their picture, then the turns (the partner's line, a suggested reply, the cue in the language being written), reorder or remove; a partner needs at least one turn and turns need a partner. Day 5 (`ChallengeEditor`): the challenge's name and instruction (English and the language being written), the tasks (the same pair, reorder or remove), and the useful phrases one per line; a challenge needs its English name and at least one task. Day 6 (`ReviewEditor`): a note on what the review repeats, then one part at a time — the quiz (`QuizEditor`: what is asked in English and in the language being written, the right answer, the other choices one per line), the review's conversation (`DialogueEditor` again) and its role-play (`RoleplayEditor` again); a part out of sight that is unfinished is named beside the part picker. Day 7 (`ScenariosEditor`): the week's scenarios one at a time — a name (English and the language being written), then its role-play in `RoleplayEditor` again — with add, reorder and remove; a scenario needs its English name, a partner and at least one turn, and one out of sight that is unfinished is named beside the scenario picker. The levels have nothing to write. Unfinished entries block saving (`validateDialogue`, `validateVocabulary`, `validateSentences`, `validateRoleplay`, `validateChallenge`, `validateQuiz`, `validateScenarios`) wherever they are, and the page says in which week and day. "Use built-in" / "Remove" drops the admin's version for that week. The page itself only picks the week, the day and the language; **every day's draft, editor, validation and week-picker count live in `useLessonContent` (`features/admin/hooks`), and a new day is added there**: its settings draft (joined to the one Save bar by `combineDrafts`), `weekContentEditor` for "the admin's version, else the built-in one, else nothing", and an entry in `lessonDays`, `unfinished` and `filled` (Day 6 has three drafts, returned together as `review`; Day 7's is `scenarios`). One-per-line fields use `toLines`, and per-language entries `withLanguage`, from `features/admin/lib/lines.ts`.
- **Where the learner is** comes from `useJourneyProgress()` (`features/home/lib/journeyProgress.ts`). **It is a stop-gap: every learner is at Week 1 and has completed nothing.** This contradicts the placement rule that not everyone starts at Week 1; replace it once a level-to-section mapping is decided (`TODO(placement)`) and lessons record progress (`TODO(lessons)`).
- **Bottom navigation:** `TabsLayout` renders `BottomNav` / `BottomNavItem` (`shared/ui`) with four tabs — Home, Learn, Progress, Profile — as router `NavLink`s; the current tab is marked by `aria-current="page"`, a bar and a heavier label, not by colour alone. It is sticky at the bottom of the phone-width column. Practice is not a tab.
- Numbers shown from data (week numbers, ranges) go through `formatNumber(language, n)` from `@/shared/lib/i18n`: Bengali digits in Bengali, Latin digits in Hindi and English, like the hand-written texts.

### Profile and its settings

- **Profile is a menu, not a page of settings.** `/profile` (`ProfilePage`, under `TabsLayout`) shows what the app knows about the learner (`ProfileSummaryCard`) and a list of rows (`SettingsMenu`, built from `ListItem`). **Each setting is its own full-bleed screen** under `/profile/` (`profileSettingsRoutes`), framed by `ProfileSubScreen`: a `StepScreen` with a back arrow to Profile and no bottom navigation. A new setting is a path, a page and a row; it is never added to `ProfilePage` itself.
- **A row's second line is the setting's current value** (the language's own name, the English voice's name, the tutor's face, the theme's name), so the menu can be read without opening anything.
- **Only what is built has a row.** The design's Notifications, Download Content, Help & Support, Sign Out and "Edit profile" are left out until those features exist (`TODO(auth)` for the last two).
- **The Account row says who is signed in**: its second line is their email, and it opens `/sign-in`, where the account screen says who they are and signs them out. Offline, when the server has not said who they are, the row has no second line. Signing out there clears this browser of everything of theirs, which is kept with the account ("A learner's data" under Backend). The account screen's back arrow leads to `/`, so from there it lands on Home, not back on Profile.
- **The card shows the learner's picture, and has no name yet** (`TODO(learner)`). The picture is, in this order: **their own photo**, chosen with the camera button on its corner; else **the picture of the Google account they signed in with**; else the age group's picture (`ProfileAvatar`, the coin of both pictures, since the learner's gender is not asked), which is also what is drawn when Google's picture cannot be loaded. Beside it: the starting level once the placement test has been taken (`usePlacementResult`, `levelLabel`) and the week (`useJourneyProgress`, still the stop-gap described under Lessons).
- **The camera** (`ProfilePhoto` in `features/profile/components`, wired by `useProfilePhoto`) opens the phone's own chooser (`accept="image/*"`: the camera or the gallery). The photo is shrunk and re-encoded in the browser (`fileToStoredImage`, to 512px) and kept in `useProfilePhotoStore` (`shared/lib/learner/profilePhoto.ts`), **and with their account**, so it follows them to another phone and is shown to nobody else; the card says so ("This photo is saved with your account. Only you see it.") beside "Remove photo", which takes it from the account too and brings back Google's picture or the stand-in. A file that is no picture, or one that cannot be kept, is refused with a reason and changes nothing. One too heavy for the server stays on that phone only.
- **Google's picture is an address, not a copy**: at each Google sign-in the server keeps the `https` address Google gives (`users.picture_url`, through `safePictureUrl`) and sends it with who is signed in (`SessionUser.pictureUrl`; `null` for an account made with an email). The app shows it only if it is `https`, asks for it with `referrerPolicy="no-referrer"`, and has nothing to show offline but the stand-in.
- **Language, Appearance and Tutor avatar save on the tap**; the first two have no pinned button, and the third's is its play check; **Voice settings saves on "Set as tutor voice"**, because a voice is tried out before it is chosen.
- **Voice settings** (`VoiceSettingsPage`, `useVoiceChoice`): a language (English first, then the `languages` settings), whose voice is being chosen (`ChoiceChips`, two tiles: Female tutor and Male tutor, in the order of the tabs under them, each naming the voice that tutor has now; it opens on the learner's own tutor), a kind of voice (`SegmentedControl`: Female · Male, hidden when a language has only one), the voices of that kind (`VoiceList`, a `ChoiceList` whose rows each have a play button), the sample sentence written out, and the pinned button with a line above it that says why it is locked or what was just set.
- **There are two voices per language, one for the male tutor and one for the female** (`useVoiceStore`: `voices[language][kind]`, kept with the account). **Any voice can be given to either tutor**: the kinds only sort the list. Until one is chosen, a tutor has the default voice of their kind (`voiceForFace`; that voice carries the "Default" mark). A choice saved by the earlier build, which had one voice per language, is dropped: which tutor it was for is not known.
- **The app speaks with the voice of the learner's tutor.** Whatever is said aloud (the placement test, Days 1 to 7, the tutor's own sample) uses the voice of the tutor chosen in Profile › Tutor avatar (`tutorVoiceKind`): changing the tutor's face changes the voice of the lessons with it.
- **The voices are the server's** (see "Voices" above): the same list on every phone, and every voice says whether it is a woman's or a man's, so there is no third group. A language the server cannot speak yet says so ("There are no voices for {language} yet": one an admin added); when the list cannot be loaded, the screen says that instead and offers nothing to set.
- **A voice goes by its own name** ("Heart", "George"), which is not a text of ours and is not translated; the saved choice is its id (`af_heart`), not its name. The default of each kind is marked "Default". A choice saved while the app still spoke with the device's voices names nothing the server has, and is passed over.
- **Under the name a row says its accent, not how the voice sounds** (`accentName`, from `Intl.DisplayNames`: "English (United Kingdom)"). The design's "Clear and friendly" lines are left out; the sample is how a learner finds that out.
- **Tutor avatar** (`TutorAvatarPage`, `useAvatarCheck`): the learner chooses the tutor's face from the drawn avatars (`tutorAvatars` in `shared/lib/learner/tutorAvatar.ts`: male, female; fixed in code, because each is a drawing of ours, not an upload), shown large above the two choices (`ChoiceList`, each with a small `TutorAvatar`). The choice is in `useTutorAvatarStore`; `useTutorAvatar()` gives it, or the default (`male`) until one is made. **"Play a sample" is the play check**: the tutor says the English sample (`voice.sample`) with its lips moving, then gives a thumbs up for a moment, and smiles the rest of the time; a learner whose sample cannot be played is told the lips will not move and still sees the thumbs up.
- **Each tutor speaks with their own voice** (see Voice settings above): the play check says the sample in the voice of the face on show, names it ("Voice: Heart") and links to Voice settings, where it is changed.
- **It is "Tutor avatar", not "AI tutor avatar"**, for the reason Day 4 does not say "AI": nothing listens or answers yet. **The tutor speaks on the journey screens** (see "The tutor on a screen" under the journey) **and plays the partner in the role-plays** (Days 4, 6 and 7: "Day 4's screen"); a tutor that listens and answers is the conversation feature, not built (`TODO(conversation)`).
- **The sample is a screen text read in the voice's language** (`voice.sample` through `useTFor(language)`), not in the screen's: a Hindi voice says the Hindi sample whatever language the learner reads the app in. An admin can write one for a language they add; it is English until they do.

### Placement test

`features/placement` runs the test that follows onboarding: Listen → Understand → Speak, then a result screen. `/placement-test` shows whatever the saved session has reached (a stage's introduction, a question, or the offer to continue); `/placement-test/result` shows the starting point.

- **There is no backend, so the test is local and says what it cannot do.** The adaptive engine (`lib/engine.ts`) and the scoring (`lib/scoring.ts`) are pure, rule-based functions that run in the browser; `advance()` is the only entry point screens use, so a server engine can replace them later (`TODO(backend)`). The session, the result and an event log are saved in this browser by `usePlacementStore` after every change, and validated with Zod when read back; the session and the result are kept with the learner's account too, so a test begun on one phone can be finished on another ("A learner's data" under Backend).
- **Speech is recorded but not scored.** Rating a recording needs AI on a server. A recording stays in memory for "listen / try again" and is dropped on Continue; only facts are kept (attempted, length, tries, help used). Speaking is always `notAssessed` in the result, with a reason — and a missing level is never treated as a low one. The result is `provisional` while that is so.
- **Adaptivity:** each stage is a staircase over `FOUNDATION | A1 | A2 | B1 | B2+`: right without help → one level up, right with help (text shown, translation) → same level, wrong or "not sure" → one down. Replaying audio never counts against the learner. A stage ends after 4–7 questions once the level is bracketed, or early at either end of the scale. The start level is the weaker of listening and understanding.
- **Questions** live in `data/itemBank.ts` (a starter set written by the assistant; `TODO(content)`: expert review). Bump `ASSESSMENT_VERSION` when they change: a test in progress on an older bank starts afresh. Question text is English and marked `lang="en"`; only the screen's own wording is translated.
- **Tone:** it is not an exam. No right/wrong after an answer, no countdown, no score or percentage, no "failed". "I'm not sure" is always available and opens help; translation is offered only then, only to learners with a mother tongue, and counts as support used, not as failure.
- **A Listen question is two screens in one.** First Play alone, in the middle of the screen under the heading — nothing else, and it stays that way while the sentence plays. Once it has been heard through, the question and its answers take over, with Play again and Play slowly at the top. Asking for help before playing shows the question (not the answers), since the help panel needs the room.
- **Listening audio is the app's voice** (`shared/lib/audio/speech.ts`, see "Voices"); when it cannot be played the test skips listening as `audioUnavailable` rather than failing the learner.
- **Events** (`lib/events.ts`) record what happened and when, never audio or what was said. They only go to the local log until there is an analytics service (`TODO(analytics)`).
- Other features read the outcome through `usePlacementResult()` from `@/features/placement`. "Start My Learning Journey" opens Home, the journey. Not built yet: recommended section/week and opening the journey there (`TODO(lessons)`), retaking from Profile, AI-suggested reassessment.

### Admin area, sign-in and sign-up

Build any further wording editor from them.

Browser storage is limited (about 5 MB in total); `TODO(backend)` replaces this with real uploads.

Other texts with `{name}` placeholders (`{level}`, `{language}`) are filled with `fillText` from `@/shared/lib/i18n`.
- **Its language picker** lists the languages from the `languages` settings (plus English if an admin removed it), by their own names, and saves the choice as the learner's language for the whole app.
- **Accounts** (`server/src/modules/auth`, `features/auth`, `shared/lib/account`): email and password, or Google where it is set up (next point); a session is a cookie the page cannot read, and who is signed in is asked of the server as the app starts (`loadSession`, `useSessionStore`), never kept in the browser. Form rules and every request and answer are the schemas in `@kuhedu/contracts` (`api/auth.ts`), whose messages are screen-text keys. Nothing of the app but the landing page opens without one (see "No guests" above).
- **Google sign-in goes by way of Google's own page, never a prompt of Google's in ours.** "Continue with Google" sends the browser to `GET /api/auth/google/start`, which sends it on to Google; Google sends it back to `GET /api/auth/google/callback` with a one-time code, which the server trades (with the client secret) for who it is, signs the browser in and sends it to the app's front door (an admin to `/admin`). Decided 2026-10-12: the first build asked Google's script for a token inside the page, and in a browser that was not already signed in to Google the button did nothing at all, silently. The redirect works in every browser and in the installed app, and nothing of Google's runs in the app. **Both are addresses the browser goes to, so they are the one place the app does not use `apiRequest`** (`goToGoogle` in `features/auth/lib/googleSignIn.ts`) and the server answers them only by sending the browser on: to `/sign-in?google=failed` when nobody was signed in (the screen then says so, `auth.googleFailed`), to plain `/sign-in` when Google's page was closed or refused. A `state` kept in a short-lived cookie (`kuhedu_google`, sent back with the browser) proves the answer belongs to a sign-in this browser began, and a `nonce` ties Google's answer to it. **Set-up:** `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `server/.env` (together or not at all: the server refuses to start with one), `VITE_GOOGLE_CLIENT_ID` for the app (only a switch for the button), and in the Google client the authorized redirect URI `<the app's address>/api/auth/google/callback`, to the letter. The server builds that address from the host the browser asked at, which is why whatever stands in front must pass the host on (`TRUST_PROXY` in production). **The request's `scope` is written with `%20` between its words, never `+`**: with `+` Google's sign-in page still loaded, but once an account was chosen it answered "400, malformed" (`server/test/google.test.ts` holds this). Signed in through with a real Google account in development on 2026-10-12; the production address is still to be added at Google (`TODO(ops)`).
- **An account is made by matching the code sent to its address, and not before.** Signing up keeps the address and password, signs the browser in so that it can answer for the code, and sends a 6-digit code (`codes.ts`: good for 10 minutes, 5 guesses, a new one at most once a minute, kept only as a keyed hash). `/verify-email` is where it is typed in, and **there is no way past it**: no "later". Until the code is matched (`emailVerified`), signing in, the account screen and the app's front door all lead to the code step and nowhere else, and on the server `requireVerified` keeps the account out of anything that is a learner's own: **every route for a learner's data uses `requireVerified`, never `requireUser`**. The way out of the code step is "Use a different email", which signs out.
- **An address that was never verified is nobody's account**: signing up with it again is not refused but takes the earlier attempt's place (its password and browsers go), since whoever typed it may have mistyped or may not own it. Only a verified address answers "already has an account". Someone who signs in before ever entering their code is let in as far as the code step and sent a new code.
- **The codes are sent from `Kuhedu Lingo <hello@lingo.kuhedu.com>`** (`server/src/lib/mailer.ts`), by whichever way is set up: **Resend** (`RESEND_API_KEY`, a secret, with `RESEND_FROM_EMAIL` as the address it sends as; over HTTPS, nothing installed) or, failing that, a mail server (`SMTP_URL`, a secret, sending as `MAIL_FROM`). A production server refuses to start without one of the two. **With neither, development writes each code to the server's log** instead of sending it, which is how a developer reads the code they were "sent"; and **a mail that fails to send is written there too, with why, anywhere but production** — where it is the caller's to hear of, and a code is never in the log. `npm run mail:test -w @kuhedu/server -- delivered@resend.dev` sends one mail the way the codes go and prints what the mail service said (that address is Resend's own, which takes a mail and delivers it nowhere). `server/test/mailer.test.ts` covers both ways with stand-ins. On 2026-10-12 Resend, with `lingo.kuhedu.com` verified in its account, took a test mail from that address and recorded it delivered to its own test address; **a mail to a real mailbox has not been looked at yet** (`TODO(ops)`: that it arrives, and not as spam; the domain has no DMARC record). The mail is English (`TODO(content)`: in the learner's language).
- **An admin is made only by `npm run admin:create -w @kuhedu/server -- <email>`** (it prints a password once, or takes `ADMIN_PASSWORD`); nobody becomes one by signing up, and there are no default credentials. Admin routes are guarded in the app by the `requireAdmin` loader (which keeps the screens out of sight) and on the server by its own `requireAdmin` (which is what refuses).
- Not built: Terms & Privacy on the account screen (`TODO(legal)`), and its illustration.

## 4. Component reusability

The design system in `src/shared/ui` is the single source of truth for UI. Screens are **compositions**, not one-off styling.

1. **Check before creating.** Before writing any new UI, look in `src/shared/ui` and the current feature's `components/`. Extend an existing component (new variant/prop) instead of duplicating it.
2. **Rule of two.** When the same UI pattern appears in a second place, extract it. Feature-specific → `features/x/components`; used by more than one feature → `shared/ui`.
3. **Layered components:**
   - _Primitives_: `Button`, `IconButton`, `Text`, `Heading`, `Card`, `Avatar`, `Badge`, `Input`, `Switch`, `ProgressBar`, `Skeleton`, `Spinner`.
   - _Patterns_: `BottomSheet`, `Dialog`, `Toast`, `ListItem`, `EmptyState`, `ErrorState`, `TopBar`, `BottomNav`, `SegmentedControl`, `Chip`.
   - _Feature components_: `ChatBubble`, `MicButton`, `Waveform`, `PronunciationScore`, `LessonCard`, built from the layers above.
   - _Built so far_ (`src/shared/ui`): `Button` (variants `primary | secondary | outline | ghost`, sizes `sm | md | lg` — `sm` is for a bar with little room: the same 44px target, less padding, smaller text — `fullWidth`, `asChild`), `ChoiceList` (single-choice list of tappable cards with optional media and description — use it for every "pick one" question; `disabled` once the choice is made and may not change; an option can carry an `action`, a control of its own such as a play button, drawn in the card beside the choice and never inside its label), `ListItem` (one row of a menu: icon, title, an optional second line and an arrow onward; `asChild` with an empty router `<Link />` makes the row a link), `ProfileAvatar` (a circular picture that turns like a coin between a male and a female image), `MaleAvatar` and `FemaleAvatar` (drawn, head and shoulders, sizes `sm | md | lg`: each blinks, its `mouth` takes a `MouthShape` — give it `useLipSync()` to move the lips with the app's voice, by the timings the server sends with each sound — and its `mood` is `neutral`, `smile` (a gentle one, lips together and corners lifted, for as long as nothing is being said: a face that grins at a learner all that time is too much) or `encourage` (the smile with a thumbs up); decoration unless given a `label`. They are shaded to look round and lit, like a 3D cartoon character, with gradients only (`AvatarDefs` defines them per avatar, `avatarPaint(useId())` names them, since several avatars can share a screen): they are SVG drawings, not 3D renders. While it speaks (its `mouth` is anything but `rest`) the head moves very slightly, as a speaker's does (`AvatarHead`). They share `AvatarFrame`, `AvatarDefs`, `AvatarHead`, `AvatarEye`, `AvatarMouth` and `AvatarThumbsUp`, and a further avatar is built from those), `TutorBar` (the tutor's place on a screen, in two rows: the face at `md` size centred in the first, what the tutor says in a speech bubble across the second, its tail pointing up at the face, and — only where there is something to hear — the face as a button that says it again and a mute button laid over the first row's end, so the face stays centred with or without it; a `leading` slot puts a screen's own control, a back arrow, at that row's start; the whole is a panel in `bg-primary-soft`; pure, wired up by `TutorNarrator` in `shared/lib/tutor`), `TutorAvatar` (draws the avatar whose id it is given: the learner's choice, or one on offer), `LanguageChoiceList` (a `ChoiceList` of languages, each with its `LanguageFlag` and its own name in its own script), `IconButton` (icon-only, `label` required, `asChild` for links), `TextField` / `TextAreaField` / `SelectField` (label, hint and error wired up; shared look via `fieldStyles.ts`; `TextField` also takes `startAdornment` / `endAdornment`), `PasswordField` (a `TextField` with a show/hide button), `CompactSelect` (pill-shaped native select with a hidden label, for headers and toolbars), `ChoiceChips` (a few short exclusive choices under a visible heading, for settings picked before a step: `wrap` for chips as wide as their text, `equal` for one row of label-over-description tiles; an option can carry a `mark`, e.g. a tick with a hidden "Done"; `tone="hero"` draws it in the on-image colors, for the scrim over a photograph; a `value` that is none of the options ticks nothing), `SegmentedControl` (row of exclusive choices; scrolls, or `fullWidth` to share the width equally), `BottomNav` + `BottomNavItem` (the main destinations along the bottom edge; an item takes `asChild` for a router link), `StepScreen` (frame for one step of a flow: optional top bar — `topBarTone="soft"` draws it as a band in the soft primary colour, edge to edge and over the notch — optional small `media` (a medal) and `eyebrow` above the heading, heading, subtitle (`subtitleTone="strong"` when the subtitle is the point of the screen), scrollable content, pinned action, which a screen that saves as it is used leaves out; the content sits in a column as tall as the free space, so a child with `flex-1` can fill or centre in it), `ProgressBar` (`value` 0–1, named by `label`), `BrandLockup` (logo + name + tagline), `BigRoundButton` (the one large control of an audio step: play, stop or record; `pulsing` while sound is playing or being recorded), `MicButton` (a `BigRoundButton` that starts and stops a recording by tap-to-toggle or press-and-hold), `ScenePicture` (a 16:9 picture of a situation with a drawn stand-in when there is none; children are laid over it, e.g. a play button).
4. **API design:**
   - Variants via a `variant` / `size` prop mapped with `cva` (class-variance-authority). No boolean prop explosions (`isPrimary`, `isLarge`, ...).
   - Forward refs and spread remaining native props (`...rest`) onto the root element so components work with forms, Radix and tests.
   - Accept `className` for layout adjustments only (margin, grid placement), and merge it with `cn()` (`clsx` + `tailwind-merge`). Do not use it to restyle a component's internals.
   - Prefer composition (`children`, compound components like `<Card.Header>`) over large prop configurations.
   - Use `asChild` (Radix `Slot`) when a component must render as a link or other element.
5. **Presentational vs. container.** `shared/ui` components are pure: no data fetching, no global store access, no routing side effects. Data wiring happens in feature-level containers/hooks.
6. **No magic values.** Colors, spacing, radii, shadows, z-index, durations and easings come from tokens. Never hard-code hex values or arbitrary pixel values (`p-[13px]`) in components.
7. **Typed and documented.** Export prop types (`ButtonProps`). Add a short JSDoc on non-obvious props.

## 5. Mobile-first UI/UX standards

The bar is **native-app quality**. If it would feel out of place next to a top-tier iOS/Android app, it is not done.

### Layout

- Write base styles for a **360px-wide** viewport; add `sm:`/`md:`/`lg:` enhancements upward. Never design desktop-first and shrink.
- Test widths: 320 (small), 360/390/430 (common phones), 768 (tablet), 1280 (desktop). No horizontal scroll at any width.
- On large screens the learner app is shown in a phone frame (below); the admin area uses the width. Do not stretch phone UI across a monitor.
- Full-height learner screens use `h-viewport` / `min-h-viewport` — never `h-dvh`, `min-h-dvh` or `100vh`, which are the browser window, not the phone. Outside the learner app (the admin area) use `100dvh`, never `100vh`.
- Respect safe areas: `env(safe-area-inset-*)` for top bars, bottom nav, sticky footers and FABs. Use `viewport-fit=cover` in the viewport meta.
- Keep primary actions in the **thumb zone** (bottom third). Use a bottom navigation (max 5 items), bottom sheets instead of centered modals, and sticky bottom CTAs.
- Handle the on-screen keyboard: inputs stay visible when focused (use the `visualViewport` API where needed), and the chat composer docks above the keyboard.

### The phone frame

- **On a tablet or anything wider, learner screens are drawn inside a phone in the middle of the display, and that phone is their viewport** (`PhoneFrame`, `app/layouts`; used by `PhoneLayout` and by `RouteError`). On a phone nothing changes: the column is the screen and the page scrolls.
- **When:** the `framed:` variant (`base.css`): at least 48rem wide **and** 40rem tall. The height matters — a phone held sideways is wide but has no room for a phone drawn on it, so it keeps the plain column (`max-w-lg`), as does a desktop window zoomed until it is that small.
- **Size:** tokens in `tokens.css` — the frame's screen is `--frame-width` (390px) wide and `--frame-max-height` (844px) tall, or as tall as the display leaves room for (`--frame-margin` clear above and below, `--frame-bezel` around). The bezel is `border-border-strong` on a display of its own colour, `bg-display` (`--color-display`, defined by every theme): **plainly not the phone's screen's** (asked for by the user on 2026-10-13: in the dark themes the two had been nearly one shade), lighter than the screen in a dark theme and deeper than it in a light one. Nothing is written on it.
- **Height:** inside the frame `--viewport-height` is the frame's screen (`frame-viewport`); `h-viewport` and `min-h-viewport` read it and fall back to `100dvh` on a phone. That is why learner screens must use them: `h-dvh` would be the browser window and run out of the frame.
- **Scrolling:** the frame's screen is the scroll container, so a long screen scrolls inside the phone, `sticky` (the bottom navigation) sticks to the phone's foot, and the display itself never scrolls. Tests that scroll a learner screen must scroll an element into view, not `window`. Scrollbars are hidden inside the frame (`frame-scrollbars`): a desktop's would narrow the phone's screen, and only on the screens that scroll.
- **Nothing but the frame's screen may scroll.** The phone clips with `overflow-clip`, never `overflow-hidden` (a hidden box can still be scrolled, by focus moving to something below its edge, and the whole screen then slides up inside the phone), and the frame's screen is `relative`, so an `absolute` descendant is placed in what scrolls. For the same reason a visually hidden input (`sr-only`) always sits in a `relative` label — its card, chip or row — and a scroll area inside a screen (`StepScreen`'s content) is `relative` too.
- **Overlays:** the frame is the containing block for `position: fixed` descendants (it has a transform), so a fixed element stays inside the phone. A portal renders outside it: when `BottomSheet`, `Dialog` and `Toast` are built, they must portal into the frame, not `document.body` (`TODO(ui)`).
- **Do not use `sm:` / `md:` / `lg:` in learner screens.** They answer to the browser window, which is wide when the frame is on, while the screen itself is always phone-wide. Learner UI is written once, for the phone. (The admin area is not framed and uses them freely.)
- Safe areas are zero inside the frame (it is a drawing, not a device), so `pt-safe` / `pb-safe` cost nothing there.

### Visual design

- Spacing on a **4px grid** (tokens: 1=4px, 2=8px, 3=12px, 4=16px, 6=24px, 8=32px). Default screen gutter: 16px.
- Type scale from tokens. Body text **≥ 16px** (this also prevents iOS zoom-on-focus). Line height 1.4–1.6. Fonts: Nunito for Latin text; Baloo Da 2 supplies Bengali glyphs and Baloo 2 Devanagari (Hindi) ones, each downloaded only when its script is on screen. These are the built-in languages; scripts of languages an admin adds later (Tamil, ...) use the device's own fonts. Always set `lang` on text in another language (e.g. `lang="bn"`).
- Use clear visual hierarchy: one primary action per screen, with secondary actions visually quieter.
- **Named themes, chosen by the user.** Each theme is one complete look (light or dark): Indigo Dawn (default), Morning Bliss, Sage Dusk, Midnight Iris, plus "Auto" (follows the device: Indigo Dawn / Midnight Iris). Components use semantic token utilities only, so they work in every theme without `dark:` variants; never write a color that assumes a particular theme.
  - A theme = one `[data-theme='<id>']` block in `tokens.css` + an entry in `src/shared/theme/themes.ts` + a name in `en.ts` + its id in the boot script in `index.html`. `themes.contrast.test.ts` enforces that every theme defines every token and meets WCAG AA.
  - `<html data-theme data-scheme>` is set before first paint by the boot script and kept in sync by `useApplyTheme`. `data-theme` also works on any subtree (used for the picker previews); a subtree must set its own `bg-*`/`text-*` classes because inherited colors are already resolved.
  - Text over photos uses `text-on-hero` / `text-on-hero-muted` on a `bg-hero-scrim` scrim sized by the text itself, never by a fixed share of the screen.
- Color contrast meets **WCAG AA** (4.5:1 text, 3:1 large text and UI components).
- Design for all states of every screen: **loading (skeletons, not spinners, for content), empty, error, offline, success**, plus partial data.
- Avoid generic "template" looks. The tutor experience should feel warm, encouraging and personal: friendly illustration/avatar, celebratory micro-moments for streaks and wins.

### Motion

- Motion should communicate (state change, spatial relationship, feedback), not decorate.
- Durations: 100–200ms for micro-interactions, 200–350ms for screen/sheet transitions. Use token easings.
- Content that takes turns in one place (see `HeadlineSlider`): stack every item in the same grid cell so the block is as tall as the tallest and nothing below moves; hide the inactive ones with `invisible` + `aria-hidden`; animate the pair with `animate-slide-out-left` / `animate-slide-in-left`; clip sideways with `overflow-x-clip` on a wrapper that reaches the screen edges. Do not rotate while `document.hidden`.
- Content that takes over a screen in place (the question and answers of a Listen question, once the sentence has been heard) fades in as one piece with `animate-fade-in`; it does not slide.
- Looping animation is rare and must carry meaning. The cases so far: the headline rotation above, `animate-pulse-ring` (a ring around a control while sound is playing or being recorded), `animate-blink` (a drawn face's closed eyelids, shown for a moment every few seconds: only their opacity changes, and without motion the eyes stay open), `animate-head-sway` with `animate-head-nod` (a drawn head while it speaks: a sway of about 2° around the neck and a lift of a unit or two, on two nested groups with different lengths so the pair does not read as a loop; when the speaking stops they are paused where they are, not removed, so the head never snaps upright; none at all without motion), and `animate-coin-flip`, which turns a two-faced coin (`ProfileAvatar`: male picture on the front, female on the back). For 3D turns, put `perspective-*` on an outer element that does not clip, `transform-3d` on the turning element, and `backface-hidden` on each face (round the faces themselves; `overflow-hidden` on an ancestor flattens the 3D). Anything that loops needs a still fallback via `motion-reduce:`.
- Animate only `transform` and `opacity`. No animating layout properties on scrolling content.
- Honor `prefers-reduced-motion`: replace movement with fades or no animation.

## 6. Touch & interaction

- **Touch targets ≥ 44×44 CSS px** (48 preferred), with ≥ 8px between adjacent targets. Expand hit areas with padding or pseudo-elements when the visual is smaller.
- Every interactive element gives **immediate feedback** (< 100ms): pressed state (`active:` scale/opacity), plus a ripple or highlight where appropriate. Remove the default tap flash with `-webkit-tap-highlight-color: transparent` and provide our own.
- No hover-only functionality. Hover styles go behind `@media (hover: hover)`.
- Use `touch-action: manipulation` on interactive controls to remove double-tap-zoom delay. Do **not** disable user zoom in the viewport meta.
- Gestures (swipe to dismiss a sheet, pull to refresh, swipe between cards) are **enhancements**. Each must have a visible button alternative.
- Use **Pointer Events** (`onPointerDown/Up/Cancel`) rather than separate mouse/touch handlers. Always handle `pointercancel`.
- **Haptics:** use the `useHaptics` hook (wrapping `navigator.vibrate`, feature-detected) for key moments: recording start/stop, correct answer, error. Keep it subtle and let users disable it.
- Prevent accidental actions: confirm destructive actions, and offer undo (via toast) where possible.
- Use `overscroll-behavior: contain` on scroll containers inside sheets and the chat list to avoid scroll chaining and accidental pull-to-refresh.
- Set the correct `inputmode`, `enterkeyhint`, `autocomplete` and `autocapitalize` on every input.

## 7. Voice & audio (core to this app)

- **Mic permission UX:** never request microphone access on load. Explain why first (a pre-permission screen), request it on a user tap, and handle _denied_ and _unavailable_ states with recovery instructions per platform. Once the browser has allowed it, a screen that said so beforehand may open it without a tap (the role-play's turns).
- Recording control: support both **tap-to-toggle** and **press-and-hold** on the `MicButton`, with a clear recording state (color, pulse, live waveform, timer), haptic on start/stop, and slide-to-cancel when holding.
- **iOS Safari quirks:** create/resume `AudioContext` only inside a user gesture; test `getUserMedia` and `MediaRecorder` in Safari and in standalone (installed) PWA mode; detect supported MIME types (`audio/webm` vs `audio/mp4`) and do not assume one.
- Stream audio and AI responses where possible to cut perceived latency. Show a "tutor is thinking/speaking" state immediately.
- Always show a **text transcript** alongside audio (accessibility, noisy environments, learning value). Offer replay and slower playback of tutor audio.
- **Every spoken text is the server's sound of it, in the voice of the learner's tutor for its language**: `speakAll` picks the one saved in `useVoiceStore` for that kind of tutor if the server still offers it, else that kind's default (`voiceForFace`); a second speaker (`SpeechPart.speaker`) gets the other tutor's (`voiceForSpeaker`). **The one exception is a person of the content's own** (`SpeechPart.voice`: a woman or a man in a conversation), who gets the default voice of that kind whatever the learner chose. `SpeakOptions.voiceId` says a text in one particular voice, for trying a voice out; nothing else should pass it. **Never the device's own text-to-speech**: see §3, "Voices".
- **One shared player, unlocked by the first tap.** A phone lets a sound start by itself (after its fetch, or when a screen opens) only on a player the learner has already started with a tap, so `speech.ts` keeps one `<audio>` for everything and plays a silent sound on it inside the first tap anywhere. Check on a real iPhone, as with the microphone.
- **Speech that starts by itself** (the tutor's line when a screen opens, `useTutorNarration`) has rules of its own: never before the learner has touched the page (`navigator.userActivation.hasBeenActive`), never when muted, only in a voice of the text's own language, always written as well, and with a mute control that is remembered. A browser that will not start it (iOS may not, outside a tap) leaves the line written and a tap away. Do not add other speech that starts by itself without the same four.
- **A face's lips follow the sound itself.** With every sound the server sends the mouth for it (§3, "Voices": which of five shapes the lips have, and from which thousandth of a second). `speech.ts` reads it with the sound and passes it on through `onSpeechActivity` (`start` with the text of each part and its `PlayingSound`: the `mouth`, and the player's `position` and `duration`; then `end`), whoever asked for the speech. `useLipSync()` asks the player on every animation frame how far into the sound it is and takes the shape for that moment (`mouthAt`), so the lips keep time when a sound is played slowly, when it stalls and through its pauses; nothing runs on a timer of its own. A sound that came without a mouth gets a likely one from its spelling spread over its length (`guessedMouth`: plausible for English, merely moving for other scripts). With reduced motion the mouth opens while the voice speaks and stays still. **Timing is the server's and exact; the shapes are a drawing's simplification** (five shapes for every sound of three languages): do not build anything that reads meaning into a shape.
- Release the mic (stop all tracks) when recording ends, when the screen loses visibility, and on unmount.
- Use the Screen Wake Lock API during active conversation sessions (feature-detected): `useWakeLock(active)` in `shared/hooks`, used by Day 4's role-play.
- All audio/speech logic lives in `shared/lib/audio` and feature hooks, not inside UI components. Built so far: `speech.ts` (the one seam for everything said: it fetches the server's sound of each text, each as the one before it arrives, and plays them in turn; English unless given a `lang`, for which `hasVoiceFor` says whether there is a voice), `speechCatalogue.ts` (the server's voices: asked for once a session, the last answer kept in this browser so that sounds already kept still play offline), `useSpeechPlayback` (plays text, tracks playing / failed, stops when the screen is hidden), `useVoiceAvailable` (whether there is a voice for a learner's language, once the voices have loaded), `voices.ts` (pure: `voicesFor` gives a language's voices in the server's order, `voiceForFace` a tutor's, `voiceForSpeaker` a speaker's in a conversation), `useVoices` (the server's voices, live), `useVoiceStore` (the learner's two voices per language, one for each kind of tutor, chosen in Profile › Voice settings), `microphone.ts` (asking for the microphone, and telling `denied` from `unavailable`), `wav.ts` (a browser's own recording as a one-channel WAV at a rate asked for, which is how a recording is sent to the server; `canMakeWav` says whether this browser can), `recorder.ts` (one recording at a time, MIME type detected, microphone released the moment it ends; it hands out the `stream` it records, for listening meanwhile), `voiceActivity.ts` (whether someone is speaking into an open microphone, **by loudness alone**: sound held clearly above the room's own level, which it learns from the quiet stretches. `prepareListening()` starts the one `AudioContext` and must be called from a tap; `listenForVoice` gives `null` where sound cannot be measured. Nothing that must be right may depend on it, and its thresholds are untuned guesses: check them on a mid-range Android in a noisy room). `microphone.ts` also knows, without asking, whether the microphone is already allowed (`primeMicrophonePermission`, `microphoneAllowed`): **the one case in which it may be opened without a tap**. The microphone needs a secure page: the LAN dev server over plain `http://` reports it as unavailable, so test recording on `localhost` or over HTTPS.
- `MicButton` (`shared/ui`, built on `BigRoundButton`) supports tap-to-toggle and press-and-hold. `useVoiceRecording` (`shared/lib/audio`) is one spoken attempt: record, play back, record again, `reset` to forget it; the take stays in memory only. Its options are all off unless given: `maxDurationMs` (else the recorder's 30 seconds), `listen` (also report `voice`: whether a voice has been heard and how long it has been quiet; `null` where the device cannot tell), `onProgress` (told several times a second while recording — the place for rules that end a recording, so they run as an event and not in an effect), `keepTake` (the earlier take goes only when a new one replaces it) and, with it, `cancel` (close the microphone, make nothing of it, keep the earlier take). `MicrophoneHelp` (`shared/lib/audio`) explains a blocked or missing microphone, with its texts under `microphone.*`. `TODO(conversation)`: live waveform and slide-to-cancel.

## 8. PWA requirements

- Valid manifest: name, short_name, `display: standalone`, theme/background colors (light + dark), `start_url`, `scope`, maskable + regular icons (192, 512), and screenshots for the richer install UI.
- Service worker via `vite-plugin-pwa` with `registerType: 'prompt'`. Show an "Update available" toast and never silently reload mid-session.
- Caching strategy: precache the app shell; lesson content from the network while it can be had, else the last answer kept (`NetworkFirst`: an admin's change must reach a learner at their next look); stale-while-revalidate for images; network-only for AI conversation endpoints.
- **Offline:** the app shell, downloaded lessons, vocabulary review and progress history work offline. AI conversation shows a clear offline state. Queue progress writes and sync when back online.
- Custom install prompt (`beforeinstallprompt`) shown at a meaningful moment (e.g. after the first completed session), never on first load. Provide iOS "Add to Home Screen" instructions.
- Use the standalone display mode to adjust UI (`@media (display-mode: standalone)`), for example hiding web-only install banners.

## 9. Performance budgets

- Targets on a mid-range Android over 4G: **LCP < 2.5s, INP < 200ms, CLS < 0.1**. Lighthouse PWA/Performance/Accessibility ≥ 90.
- Initial JS **< 170KB gzipped**. Code-split every route with `React.lazy`, and lazy-load heavy modules (audio visualizers, charts, confetti).
- Images: AVIF/WebP, explicit `width`/`height`, `loading="lazy"` below the fold. Prefer SVG for icons and illustrations.
- Fonts: self-hosted, subset, `font-display: swap`, preload only the primary weight.
- Virtualize long lists (chat history, vocabulary).
- Avoid unnecessary re-renders: select narrow slices from Zustand, memoize only where profiling shows a need.

## 10. Accessibility

- Semantic HTML first (`button`, `nav`, `main`, headings in order). ARIA only when semantics are not enough.
- Every icon-only button has an `aria-label`. Every image has meaningful `alt` (or `alt=""` if decorative).
- Visible focus states (`focus-visible`) for keyboard and switch users.
- Live regions (`aria-live="polite"`) announce new tutor messages and feedback results.
- Anything that changes by itself for more than 5 seconds (rotating text, carousels) needs a visible control that stops it, and must not be a live region.
- Support text scaling up to 200% without broken layouts. Use `rem` for type.
- Never convey meaning by color alone (for example, pronunciation scores also use icons or labels).

## 11. Code conventions

- TypeScript `strict`. No `any`; use `unknown` and narrow it. Validate all API responses with Zod at the boundary.
- Functional components and hooks only. Keep components under ~150 lines; extract hooks/subcomponents beyond that.
- Name event props `onXxx` and handlers `handleXxx`.
- No inline styles except for dynamic values (e.g. waveform heights). Use Tailwind classes with tokens.
- Learner-facing text goes through `useT()` and the catalogs (see §3, "Screen texts and languages"); admin wording through `adminText`. No literal UI strings in components.
- Handle errors explicitly: an error boundary per route, user-friendly messages, and retry actions.
- Write comments only for _why_, not _what_.

## 12. Security & privacy

- **Never put AI/LLM, speech or other secret API keys in client code.** All AI calls go through our backend/API proxy. Speech is scored by our own `speech/` service, not sent to a paid speech API (§3, "Speech scoring"). Server secrets (the database password included) live in `server/.env` or the host's environment, nowhere else.
- Treat voice recordings as sensitive personal data: explain retention, provide delete-my-data, and do not log raw audio or transcripts to analytics. **A recording leaves the phone only on a tap that says so, and is kept nowhere** (a word's check and a reply's: §3, "Speech scoring" and "Checking a reply"), and neither are the words made of it; anything that would keep one, or send one without that tap, is a new decision.
- Sanitize any rendered AI output. Never use `dangerouslySetInnerHTML` with model output.
- **What is kept of a learner is theirs alone**: `/api/me/*` takes whose it is from the session and from nothing in the request, and a learner's photo is given to nobody but them. **A browser that is signed out holds none of it** (§3, "A learner's data").
- **Who someone is, is the server's to say.** The app's own checks (`requireAccount`, `requireAdmin`, `requireUnverified`, the front door) only decide which screen to show; what must be protected is refused on the server (`requireVerified`, `requireAdmin` in `server/src/plugins/session.ts`). An emailed code is never logged where real people use the server, and never kept as it was sent.
- Anything read from browser storage (settings, saved answers, session) is untrusted input: validate it with its schema or a type guard before use, as the existing stores and `useAppConfig` do.

## 13. Testing & definition of done

A change is **done** only when:

- [ ] It works at 360px width and at desktop width (learner screens: inside the phone frame), in every named theme (check at least one light and one dark).
- [ ] Touch targets, pressed states and safe areas have been checked.
- [ ] Loading, empty, error and offline states exist where relevant.
- [ ] It is keyboard and screen-reader usable (labels, focus, live regions).
- [ ] It reuses `shared/ui` components; any new reusable piece was added there.
- [ ] `npm run lint`, `npm run typecheck` and `npm test` pass.
- [ ] Shared UI components and key hooks have unit tests; critical flows (onboarding, a conversation turn) have Playwright tests on a mobile viewport (e.g. Pixel 7, iPhone 14).

Notes:

- Styling tokens live in `src/shared/styles/tokens.css`. Tailwind's default palette, type scale, radii and shadows are **cleared**, so only token utilities exist (`bg-surface`, `text-fg-muted`, `bg-primary`, `rounded-lg`, `shadow-md`, ...). Spacing uses Tailwind's default 4px scale. Custom utilities: `pt-safe`, `pb-safe`, `px-safe`, `px-gutter`, `touch-target`, `sticky-screen-top` (a bar that stays at the top of a screen which scrolls as a whole, reaching both edges and covering the notch), `scroll-contained`, `h-viewport`, `min-h-viewport`, `frame-viewport`, `frame-scrollbars`, the `framed:` variant, `animate-rise-in`, `animate-fade-in`, `animate-coin-flip`, `animate-pulse-ring`, `animate-blink`, `animate-head-sway`, `animate-head-nod`, `animate-slide-in-left`, `animate-slide-out-left`.
- A drawn person's colors are the `--figure-*` tokens in `tokens.css` (`fill-(--figure-skin)`, `stroke-(--figure-lip)`): the figure's own, so the same in every theme (gradient stops take them as `[stop-color:var(--figure-skin)]`), and not part of the per-theme color set that `themes.contrast.test.ts` checks.
- Bundled default artwork lives in `public/` (the logo, `flags/`, `avatars/`) and is what settings fall back to. The flags and avatars are placeholder drawings, meant to be replaced through Admin settings.
- **The logo is one picture, `public/logo.png`**, and everything else is made from it by `npm run generate-pwa-assets` (`pwa-assets.config.ts`): the favicon, the installed-app icons, and the logo the landing and account screens show by default, which is the 192px icon (`/pwa-192x192.png`, 7 KB) and not the picture itself (210 KB, left out of the service worker's precache). It is a letter in several colors on a see-through background, so the icons that must be filled are filled with white.
- Import `ThemePicker` from `@/shared/theme/ThemePicker`, not the `@/shared/theme` barrel: the app shell imports the barrel, and anything exported there lands in the initial bundle.
- Playwright runs with service workers blocked so `page.route()` mocks are reliable. `e2e/helpers.ts` has `seedLanguage`, `seedSettings`, `signInAsAdmin`, `stubSpeech` (stands in for the server's speaking routes and for the player, where a sound "plays" at once; modes `works`, `fails` and `unreachable`; `spoken` reads back each text said and the id of its voice), `untouchedUntilTapped` (for a test about what happens before the first tap: Playwright's own look at the page counts as a touch) and `denyMicrophone`; side-by-side tests open two pages in one browser context. **Specs take `test` and `expect` from `e2e/helpers.ts`, not from `@playwright/test`**: that `test` starts every browser signed in as a learner with an account (`LEARNER`), since no learner screen opens otherwise. A test about a visitor says `signedInAs(page, null)`, one about a sign-up without its code `signedInAs(page, { ...LEARNER, emailVerified: false })`; `signInAsAdmin` signs the admin in through the real screen against a stand-in for the account routes (`adminServer`), for every tab of the browser. **That `test` also leaves `/api/me` unanswered** (`withoutLearnerServer`), so a spec runs on what it seeded, as the app does offline; a spec about the account's data gives its browsers `learnerServer(context, kept)` (several can share one `kept`) and, to sign out, `learnerSession`. **The lesson routes are unanswered too** (`withoutLessonServer`), so a learner's screens run on what is built in and what the spec seeded; `signInAsAdmin` gives the admin's browser a stand-in that keeps what they save (`lessonServer`), and a spec about a learner reading the server gives one itself. Nothing in a spec may reach the real account routes: `vite preview` proxies `/api` to a backend if one is running.
- The Chromium projects run with a fake microphone (`playwright.config.ts`), so the placement test's speaking part runs unattended. WebKit has none: tests that record are skipped in `iphone-14`, so check recording on a real iPhone.
- `src/test/setup.ts` gives jsdom a `matchMedia` in which no query matches (anything with a drawn avatar asks for reduced motion); a test about a media query stubs its own.
- Tests that need settings write them with `settingsRepository.write(name, value)` (unit) or `seedSettings` (e2e); reset stores and `localStorage` in `beforeEach`.
- Tailwind v4's `hover:` variant already applies only on devices that can hover.
- ESLint is pinned to v9 because `eslint-plugin-jsx-a11y` does not support v10 yet.
- Playwright's `iphone-14` project needs WebKit, which may be missing system DLLs on Windows. Run it on macOS/Linux/CI, or use `--project=pixel-7 --project=desktop` locally.
